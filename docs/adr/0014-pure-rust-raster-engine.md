# A pure-Rust raster engine, no GDAL

Status: Accepted (2026-09-28, Canopi v2; decision canopi-yr93, bead canopi-paxo)

## Context

The Data library read, converted and placed rasters by shelling out to the GDAL command-line tools (`gdalinfo`, `gdal_translate`, `gdaltransform`). GDAL was not bundled: Import and inspection said "unavailable" on every machine without a system install, and the installers could not ship it without adding a large native dependency tree (PROJ, its database, GEOS, libtiff, ...) per platform. Every raster operation ran as a child process with its own memory, cache and deadline rules.

## Decision

- **One in-process engine.** `desktop/src/services/lidar/rust_engine/` implements the `RasterEngine` seam (`engine.rs`) on the `whitebox_next_gen` crates: `wbgeotiff` (the `opengeos/whitebox-wasm` fork already pinned, patched over crates.io so `wbraster` shares it) for TIFF directories, codecs and predictors, and `wbraster` for the other formats. Nothing is discovered at run time and the engine's version names the crates.
- **One transform path for coordinate systems** (amended 2026-10-04, canopi-ji73, U24). Every transform goes through `proj4rs` with the EPSG definitions (PROJ strings and WKT) of `crs-definitions`, both pinned exactly, `proj4rs`'s own `crs-definitions` feature off. `wbprojection` only reads WKT that names no code, identifies codes and gives areas of use; it is never a fallback for a code `proj4rs` cannot read, which is refused as "EPSG:n is not supported". `crs.rs` normalises PROJ strings for `proj4rs` 0.2.0 (`+k_0` read as `+k`, `+pm` folded into `+lon_0`) until upstream fixes both.
- **The engine owns its outputs and its CRS keys.** It writes the numeric and display COG profiles with its own tiled writer (directories first, 256-pixel Float32 tiles, nodata-aware averaged overviews halving while a side exceeds a tile, the `GDAL_NODATA` tag), decodes TIFF strips and tiles itself, reads GeoTIFF keys including the conic false-origin keys the crate ignores, and writes a datum shift as `GeogTOWGS84GeoKey`, so the display renderer places a tile where the engine does.
- **Memory is bounded by the existing capacity limit, not by the raster.** A GeoTIFF converts through the one writer in row windows of whole tiles holding at most `import::MAX_RAW_EXTRACTION_CELLS` cells, at any size the admission bounds allow (2 GiB per file, 400 M cells per import checked before a source converts, free space). Each overview level is averaged from the level before it, read back from the file being written, so the output is byte-identical to a whole conversion. Cancellation is checked between windows, chunks and levels. (Amended 2026-10-03, canopi-dfc0.)
- **What cannot stream loads whole under that limit.** Uncompressed strips are read by byte range and every other chunk is decoded whole, so a GeoTIFF whose compressed chunk decodes above 64 MiB, and every other format (`wbraster` has no window API), is loaded whole after the limit, with the same named reason as any other whole-raster read. Display parts are composed at most 4×4 chunks at a time.
- **GDAL stays only as a test oracle.** `gdal_engine.rs` is compiled for tests, found on `PATH` alone, and used by the ignored comparison lane `rust_engine::comparison`, which skips cleanly without GDAL. No environment variable, CI install, guide or release note mentions GDAL as a requirement.
- **Vocabulary is unchanged.** Probes keep GDAL's driver, band type, mask flag and compression names, which the catalogue and admission rules were written against; `crs_class` still reads WKT.

## Rejected alternatives

- **Bundling GDAL** (canopi-fxil.20): 100+ MB of native libraries and data per platform, three packaging pipelines, and a child-process contract for every read.
- **`georust/proj` and the `gdal` crate bindings**: both link the C libraries, so they bundle the same tree and need it at build time on every CI runner and contributor machine.
- **`proj4rs` for the whole engine** (2026-09-28): no registry, raster stack or GeoTIFF key handling. It carries the transforms since 2026-10-04, with `crs-definitions` as its registry.
- **`wbprojection` for transforms** (until 2026-10-04): it placed the Dutch, British, Belgian, Austrian, Greek and Luxembourg grids 29–390 m off, Krovak by 1,260 km and the NTF Lambert zones by 17 km, lacked EPSG:5698 and read feet systems as metres; the engine had already replaced its Swiss and LAEA projections with its own formulas.

## Consequences and caveats

- Import, display, inspection and coverage work on every machine the installers target; only Slope still needs the GeoLibre CLI.
- The crates are young. The engine corrects their gaps itself (the false-origin keys, `proj4rs`'s `+k_0` and `+pm`) and the comparison lane is the standing proof. Measured against GDAL 3.8.4: on GDAL-authored Float32, striped, Int16 LZW predictor 2, Byte, big-endian UInt32 and Float64, PackBits and user-defined Lambert GeoTIFFs, an Esri ASCII grid, an XYZ grid and the IGN LiDAR HD tile, samples, controlled COGs and finite overview cells are identical and WGS84 extents agree within 3.4e-8 deg.
- Statistics agree within 1e-13 relative; transforms inside each CRS's area of use within 1.1e-4 m and 1e-9 deg for Lambert-93, UTM 32N/33N, Web Mercator, LV95 and LAEA Europe, and UTM stays exact 15° from its central meridian (2026-10-04). National grids are noted, not asserted: datum steps are the definitions' Helmert shifts, without grid files, so they sit about 1–5 m from a grid-based PROJ (Krovak up to 15 m).
- PROJ 9.4.0's coordinates of one point per code (`scripts/gen_crs_reference_points.sh`, no grids) are the per-code check: forward within 1 cm, 8 m for Krovak 5514 and 0.5 m for Martinique 2973, whose definition carries EPSG's 10 m Helmert shift where PROJ takes the 0.1 m one. The engine's inverse closes within 1e-8 deg, 3e-8 deg (3 mm) where a datum shift moves the ellipsoidal height a 2-D transform drops.
- The 352 non-geocentric codes `proj4rs` cannot read or would misplace (Cassini, oblique Mercator, Polyconic, NZ Map Grid, NAD27 grids, the 12 polar LAEA, 28 geographic CRSs on another meridian) are refused by name; a definition without a datum shift (Madrid 1870, EPSG:2062) is placed with none. Catalogue items imported before 2026-10-04 keep their extents and stored WKT until re-imported (ADR 0021).
- A new import stores `crs-definitions`' WKT and writes its name as the GeoTIFF citation: Lambert-93 is now "RGF93 / Lambert-93" with a zero `TOWGS84`, its numeric keys, pixels and placement unchanged, and its display tiles regenerate with the v2 profile.
- A CRS without a code is written back as GeoTIFF keys in metres, so a PROJ string in another linear unit, or a WKT naming no code whose `EXTENSION["PROJ4",..]` is in one, is refused rather than identified by its parameters.
- GeoTIFF sources import at any admitted size, as they did with GDAL. A large source in another format, or a GeoTIFF stored as one huge compressed strip, is still refused by name above 25 M cells; the fix is to rewrite it as a tiled GeoTIFF.
- GDAL counted `±inf` samples as values; Canopi's validity rule (finite and not NoData) now applies to statistics and overviews alike.
- A bump of any of these crates re-runs the comparison lane and regenerates the reference points before it merges (advice); a `proj4rs` bump that reads `+k_0` and `+pm` deletes the normalisation.
