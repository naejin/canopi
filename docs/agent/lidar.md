# LiDAR implementation guide

Use this entry point for raster import, the shared library, analysis, inspection and presentation. The repaired stack is integrated for user review; see the [current receipt](../design/raster-rework/completion-receipt.md#current-correction-acceptance) for verified scope and `canopi-j571.3` for remaining qualification. The [foundation record](../design/lidar-library.md) retains storage and scientific invariants. Consult bd before claiming implementation.

The [GeoLibre adoption plan](../design/raster-rework/geolibre-adoption-plan.md) is being delivered on `feature/geolibre-adoption`; the [adoption receipt](../design/raster-rework/geolibre-adoption-receipt.md) records each slice's evidence. The fixed-item library, upstream display route, Data Library and Layers data band (S1–S3) and contextual GeoLibre slope (S4) have landed; whole-app qualification and packaging (S5) remain. Where this guide and older raster-rework records disagree, the adoption plan and this guide win. Sources keep the [ordered COG Data Layer](../design/raster-rework/ordered-cog-design.md) storage of [ADR 0002](../adr/0002-geolibre-module-reuse.md): a topmost-valid composition of retained source COGs, now frozen after its first publication.

## Current implementation

- **Fixed library items.** `services/lidar/mod.rs` exposes `import_item`/`retry_import`/`dismiss_import` (one new item per import, saved request in `lidar_import_jobs.request_json`), `rename_layer`/`rename_analysis`, guarded `delete_layer` (refused while saved results depend on it) and `delete_analysis`. A published item refuses new sources; there is no history, source editing, library Undo or automatic refresh.
- **Catalogue v2 schema, no migrations.** Canopi v2 breaks LiDAR library compatibility on purpose. `catalogue.rs` creates one schema (`CATALOGUE_VERSION` 20) and has no migration ladder or backup; `LidarLibrary::open` deletes a library whose catalogue records an older version (`discard_unsupported_library`) and `catalogue::open` refuses any other version, so a newer library is never deleted or written. Generations are ordered collections only (`lidar_collection_members`, interpretation-level `valid_cells`/range facts); dense mosaics, acceptance regions, footprints, lineage/undo columns and previous-composition members no longer exist. Do not add compatibility readers or migrations for pre-v2 data.
- **Display derivatives.** `display_cog.rs` prepares content-keyed, DEFLATE, 256-block, AVERAGE-overview COGs (profile `display-cog-deflate256-v1`) per source asset or chunk-group part, stages them outside the asset scope and renames them into `$APPDATA/lidar/display-cog/`, registers them in `display_cogs`, and answers `lidar_display_descriptor` (Preparing/Ready/Unavailable/Failed/Stale, fenced by generation). Import prepares derivatives before publication; older items prepare lazily on the one preparation lane. NoData is the -2^127 sentinel, tagged with its exact decimal.
- **Retired display route.** The PNG pyramids, on-demand `tiles.rs` renderer, `tile_cache.rs`, `lidar_raster_tile` and the `tilesets` contract are gone; `raster_info.rs` keeps the two `gdalinfo` metadata helpers analysis still uses.
- **Slope recipes.** `lidar_analysis_definitions.version` is the execution authority (`analysis::SlopeRecipe`): **2** is the pinned GeoLibre projected slope and the only recipe (Horn recipe 1 was removed with v2), 5×5 Florinsky stencil with a two-cell halo. Unknown versions and unreadable parameters fail by name; publication rechecks the stored recipe inside the transaction and records `method_id`, `recipe_version` and the engine build. Recipe 2 stages each 1024² core plus halo with the exact -2^127 NoData sentinel (the tool substitutes the valid centre for missing neighbours), keeps invalid centres invalid, and marks quality only where the whole 5×5 input was valid. `geolibre.rs` owns discovery (`CANOPI_GEOLIBRE_BIN`, beside the executable, then `PATH`) and runs `geolibre slope` through the bounded GDAL process runner with `RAYON_NUM_THREADS=2`; a missing CLI makes new slope unavailable (`snapshot.slope_engine`). The resolver/reader window cap is sized to the widest recipe halo (`prepared_raster::MAX_RECIPE_HALO`).
- **Create and Retry.** `create_analysis` always writes recipe 2 and one job pinned to the source's current generation; a second calculation is a second definition. `retry_analysis` reruns only a failed or cancelled operation, with its stored recipe and parameters, against the input its last job was pinned to; a complete result, a missing pinned input or a gone/unexpected input is refused before enqueue. The snapshot reports that pinned input for failed items, typed `method` and `engine_version`.
- **Numeric reads.** `generation.rs` (`CollectionReader`, `GenerationReader`) and `collection.rs` resolve bounded windows for analysis and inspection; `inspection.rs` samples one pixel through display admission (`admit_sample_request`). `admission.rs` keeps the unchanged 24-file/2-GiB/400M-cell import policy.
- **Frontend.** `maplibre/raster-display/` owns the upstream `maplibre-gl-raster` adapter and the two-lane worker pool (see [MapLibre](maplibre.md#lidar-raster-band); GeoLibre's own raster path was evaluated and not adopted, see [GeoLibre reuse](maplibre.md#geolibre-reuse)). `app/lidar/display.ts` owns descriptors and styles, `library-items.ts` the Data Library read model, `actions.ts` every library and reference mutation, `library-store.ts` the snapshot and polling, `inspection.ts` the inspection session. `components/panels/lidar/DataLibraryPanel.tsx` (with `LibraryPreview.tsx`) is the `data` side panel; `LidarLayersSection.tsx` is the Layers data band. There is no Analysis panel or navigation. **Calculate slope** opens a small form in the Data Library from a ready source (its menu or details, or its Layers details via `calculateSlopeInLibrary`); `slopeIneligibility` explains unsupported inputs or a missing engine. `actions.calculateSlope` records the originating Design session for a Layers-initiated run, and the workflow-owned `settleSlopeAttachments` effect adds the finished result only to that session.

The Q qualification harness (`scripts/raster-qualification/`) and the synthetic capacity-plane generator were deleted in v2; their [historical evidence](../design/raster-qualification-q.md) remains until the docs rewrite. Do not recreate them; regression coverage lives in the `services::lidar` tests. The [review/debrief](../design/raster-rework/review-and-debrief.md) owns historical outcomes and improvement evidence. GDAL and the pinned native reader remain selected; Rust owns native raster work and TypeScript application orchestration. No new Python raster tooling or wholesale Python removal.

Preserve originals/sidecars, source-specific validity, valid zero/negative values and current Float32 semantics. The candidate retains its old 24-file/2-GiB/400M input policy; lift those limits only through the source-import amendment’s bounded implementation and evidence. Source-only publication no longer requires composed-pixel measurement; source facts remain measured during preparation. [Collaboration](../design/raster-rework/collaboration-protocol.md) retains main-agent review and user courier authority.

The library owns originals, masks, numeric results, jobs and caches; a Design owns only references and presentation. Shared workspace navigation never changes raster geography or scientific results. Use the current map/camera lifecycle rather than introducing a second map owner.

For native library changes, run the focused `services::lidar` tests and repository Rust gates. The real-fixture ignored lane and its fixture variables are in the [build guide](build-release.md#lidar-raster-engine); a run without its fixtures is not a pass, and an unavailable fixture is reported as unavailable rather than as a green lane. Frontend tests include `lidar-actions`, `lidar-library-store`, `lidar-library-items`, `lidar-data-library-panel`, `lidar-layers-section`, `lidar-display`, `raster-display-pool`, `raster-display-adapter`, `design-edit-lidar`, and `lidar-camera-navigation` under `desktop/web/src/__tests__/`. Shared contracts require generated-binding checks; shared workspace changes require the edition gates in [AGENTS.md](../../AGENTS.md#quality-gates).
