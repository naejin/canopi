# Browser edition

Use the [frontend guide](frontend-patterns.md) to select the relevant reference.

Run the real browser app from `desktop/web/` with `npm run dev:web` and open `http://localhost:1421/app/`. It uses browser storage and generated catalog assets; it is not the memory gallery. The [edition development guide](edition-development.md) owns prerequisites, isolated profiles, reset behavior, and the distinction between bundle, fixture-package, and release-catalog checks.

## Browser App Shell

- Web Edition v1 uses a Browser App Shell instead of the desktop `TitleBar`, `MenuBar`, native window controls, native File menu, or native Recent Design path menus. See `docs/adr/0005-web-edition-scope.md`.
- The implemented browser shell command set is New, Open `.canopi`, Download `.canopi`, Export to PDF, language/theme, and panel toggles. Canvas PDF uses the shared preview/layout/encoder and a browser download adapter; see the [Canvas PDF guide](canvas-pdf.md) and [ADR 0008](../adr/0008-canvas-pdf-export.md). Browser Drafts remain internal autosave/recovery state: `BrowserDesignSessionController` restores the newest valid Draft when `WebApp` starts with no active Design, while an empty store shows the Welcome Screen. Do not expose a visible Drafts command or list. Keep reveal-in-file-manager, updater, Problem Report, native save/save-as, direct save-back, Design Location, and native file-management export flows outside the web shell. Other Web export exclusions follow ADR 0024.
- The Web Edition Browser App Shell should preserve desktop chrome muscle memory: desktop-style top bar structure, menu/dropdown interaction, centered Design identity, and the right-side PanelBar pattern. Match the desktop UX shape while backing it with browser-safe shell and panel projections.
- Keep the shell thin: `WebApp` supplies the caller-ready projection composed by `web/browser-shell-commands.ts`; `BrowserAppShell` renders and invokes projected actions without owning command IDs, availability checks, navigation dispatch, or theme dispatch. Design Session actions, browser file/storage adapters, settings seams, and panel state stay behind the Web capability adapter rather than leaking into generic chrome. Do not import the Desktop command registry, Tauri IPC, IndexedDB, localStorage, or browser file APIs into the shell.
- The Browser App Shell is app chrome, not website navigation and not a reduced catalog widget. It should preserve the real Canopi workspace while making explicit `.canopi` download/export clear.
- Browser-local persistence belongs behind the [Browser App Data](#browser-app-data) store; the shell must not import storage directly.
- Web Edition no-Design state should use a desktop-style Welcome Screen with New Design and Open Design actions, but omit Recent Designs/Recent Files from the browser home surface.
- `web/WebWorkspace.tsx` supplies browser-safe surfaces to the shared `components/workspace/WorkspaceComposition.tsx`; the browser shell projection is the mounted-panel authority. Use `WebCanvasWorkspace`, `WebCanvasToolbar`, `WebLayersPanel`, and `browser-canvas-runtime.ts` instead of desktop `CanvasPanel`, `CanvasToolbar`, `DisplayLegend`, `CommandPalette`, command registry, or Desktop panel adapters. `WebCanvasWorkspace` attaches the runtime once through `browser-design-session.ts`; resolved New/Open/Template/Draft replacements then cross the platform-neutral `app/document-session/replacement.ts` seam. Calendar, Budget, and Consortium share the browser-safe planning workbenches and mount through the common responsive dock policy.
- Do not observe ordinary Web Edition `currentDesign` snapshot changes to call canvas `loadDocument()` or `replaceDocument()`. Non-canvas Design Edit changes must leave live SceneStore-owned canvas state and history intact.
- Web Edition Species UI mounts through `WebSpeciesCatalogPanel`, not the desktop `PlantDbPanel`, `FavoritesPanel`, or full `PlantDetailCard`. It consumes the shared Species Catalog Workbench projection for text search, generated Web-supported filters, active chips, detail, favorites, and recently viewed Species. Its Favorites surface shares only accent-insensitive local filtering and detail focus restoration through `components/plant-db/favorite-species-presentation.ts`. Unsupported desktop-only filters are absent rather than disabled, browser-local favorites/recently viewed Species stay Web-specific, and Web Edition Plant Detail remains reduced instead of importing the desktop `PlantDetailCard`.
- At viewport widths up to 860px, `WebSpeciesCatalogPanel` collapses supported filters into a one-line summary that reports active-filter state and expands on demand. Species rows expose a touch-friendly Place action that starts Plant Stamp so the user can tap the canvas; pointer devices may also use drag/drop.
- **Web has no Location surface** ([ADR 0001](../adr/0001-geolocated-map-canvas.md)). Place search (pin button) uses the shared geocoding provider registry through browser `fetch`, as on Desktop ([ADR 0005](../adr/0005-web-edition-scope.md)).
- **What Web must not do.** Web imports no Tauri, native or local-raster-processing code. Preserve the static-bundle, no-backend, no-proxy, no-PWA, no-offline-archive and no-bulk-download constraints of [ADR 0005](../adr/0005-web-edition-scope.md).
- **Web presents the shared provider set** with each provider's attribution, tile size and zoom ceiling. The Google key is device-local — never written to a Design, export, diagnostic bundle or error text. A provider, key or session change is reconciled into the live map and must never recreate it.
- Web Edition source should stay in this repository as a browser Vite entry/build that shares app modules with desktop. `canopi-website` should publish the built artifact only and must not import shared Canopi frontend modules directly.
- Desktop and Web Edition entries should select their platform adapters at compile time. Do not put runtime `isWeb`/`isTauri` branches in shared app modules to choose IPC, browser storage, file, catalog, shell, Canvas PDF delivery, or Budget CSV delivery behavior. See `docs/adr/0005-web-edition-scope.md`.
- Settings bootstrap follows that same composition rule: `platform/settings.desktop.ts` delegates to typed IPC, `platform/settings.browser.ts` validates browser app-data against generated Rust defaults/catalogs, and each `platform/*.ts` entry installs its adapter into the platform-neutral Settings Projection before rendering. Keep concrete storage imports out of `app/settings/projection.ts`.
- Both HTML entries own the tiny guarded `canopi-theme` cache read that sets `<html data-theme>` before module loading and first paint. `utils/theme.ts` then owns reactive DOM/cache synchronization for the active module lifetime; components and browser settings adapters must not duplicate it.
- Web Edition v1 is not offline-first. Do not add service workers, PWA install prompts, app-managed precache logic, or offline map/image promises to the browser shell without a later decision. See `docs/adr/0005-web-edition-scope.md`.


## Browser App Data

- `web/browser-app-data.ts` owns the synchronous caller API, resource schemas, normalization and storage for four independent version-2 localStorage records: Drafts, Settings, Species activity, and Saved Object Stamps. Callers must not depend on storage keys.
- Canopi v2 has no browser-storage migration: the former v1 aggregate (`canopi:web-app-data:v1`) and any v2 migration markers are ignored, never read or rewritten. A missing, corrupt or foreign record reads as empty; a failed write reports `{ ok: false }` and leaves the previous record readable.
- Settings, Species, and Stamp writes do not parse or serialize Draft bodies. Concurrent writes to the same resource are last-writer-wins.
- The compile-time browser settings adapter loads and saves the complete shared `Settings` contract through this store. `WebApp` asks the Browser Design Session to restore its newest valid Draft before installing the autosave observer; the controller owns Draft ordering and replacement. Shell and Canvas settings commands mutate `app/settings/projection.ts` rather than importing storage or receiving persistence callbacks.
