# Browser edition

Use the [frontend guide](frontend-patterns.md) to select the relevant reference.

## Browser App Shell

- Web Edition v1 uses a Browser App Shell instead of the desktop `TitleBar`, `MenuBar`, native window controls, native File menu, or native Recent Design path menus. See `docs/adr/0020-web-edition-browser-app-shell.md`.
- The implemented browser shell command set is New, Open `.canopi`, Download `.canopi`, Export to PDF, language/theme, and panel toggles. Canvas PDF uses the shared preview/layout/encoder and a browser download adapter; see the [Canvas PDF guide](canvas-pdf.md) and [ADR 0024](../adr/0024-shared-canvas-pdf-export.md). Browser Drafts remain internal autosave/recovery state; do not expose a visible Drafts command or list. Keep reveal-in-file-manager, updater, Problem Report, native save/save-as, direct save-back, Design Location, and native file-management export flows outside the web shell. Other Web export exclusions follow ADR 0024.
- The Web Edition Browser App Shell should preserve desktop chrome muscle memory: desktop-style top bar structure, menu/dropdown interaction, centered Design identity, and the right-side PanelBar pattern. Match the desktop UX shape while backing it with browser-safe shell and panel projections.
- Keep the shell thin: `WebApp` supplies the caller-ready projection composed by `web/browser-shell-commands.ts`; `BrowserAppShell` renders and invokes projected actions without owning command IDs, availability checks, navigation dispatch, or theme dispatch. Design Session actions, browser file/storage adapters, settings seams, and panel state stay behind the Web capability adapter rather than leaking into generic chrome. Do not import the Desktop command registry, Tauri IPC, IndexedDB, localStorage, or browser file APIs into the shell.
- The Browser App Shell is app chrome, not website navigation and not a reduced catalog widget. It should preserve the real Canopi workspace while making explicit `.canopi` download/export clear.
- Browser-local persistence belongs behind the [Browser App Data](#browser-app-data) store; the shell must not import storage directly.
- Web Edition no-Design state should use a desktop-style Welcome Screen with New Design and Open Design actions, but omit Recent Designs/Recent Files from the browser home surface.
- Web Edition canvas mounting lives under `desktop/web/src/web/`. Use `WebCanvasWorkspace`, `WebCanvasToolbar`, and `browser-canvas-runtime.ts` instead of desktop `CanvasPanel`, `CanvasToolbar`, `BottomPanel`, `DisplayLegend`, `CommandPalette`, command registry, Desktop `LayersPanel` adapter, or desktop Design Session lifecycle/state-machine modules. `WebCanvasWorkspace` attaches the runtime once through `browser-design-session.ts`; resolved New/Open/Template/Draft replacements then cross the platform-neutral `app/document-session/replacement.ts` seam.
- Do not observe ordinary Web Edition `currentDesign` snapshot changes to call canvas `loadDocument()` or `replaceDocument()`. Non-canvas Design Edit changes must leave live SceneStore-owned canvas state and history intact.
- Web Edition Species UI mounts through `WebSpeciesCatalogPanel`, not the desktop `PlantDbPanel`, `FavoritesPanel`, or full `PlantDetailCard`. It consumes the shared Species Catalog Workbench projection for text search, generated Web-supported filters, active chips, detail, favorites, and recently viewed Species. Unsupported desktop-only filters are absent rather than disabled, browser-local favorites/recently viewed Species stay Web-specific, and Web Edition Plant Detail remains reduced instead of importing the desktop `PlantDetailCard`.
- At viewport widths up to 860px, `WebSpeciesCatalogPanel` collapses supported filters into a one-line summary that reports active-filter state and expands on demand. Species rows expose a touch-friendly Place action that starts Plant Stamp so the user can tap the canvas; pointer devices may also use drag/drop.
- Web Edition v1 does not mount a visible Location Workbench, Design Location panel, coordinate form, or map-picking UI. Do not add `nav.location`, `WebLocationWorkspace`, or Web imports of `app/location/coordinate-workbench.ts`; saved `.canopi` Location data should still round-trip through the document model.
- Web Edition source should stay in this repository as a browser Vite entry/build that shares app modules with desktop. `canopi-website` should publish the built artifact only and must not import shared Canopi frontend modules directly.
- Desktop and Web Edition entries should select their platform adapters at compile time. Do not put runtime `isWeb`/`isTauri` branches in shared app modules to choose IPC, browser storage, file, catalog, or shell behavior. See `docs/adr/0021-web-edition-compile-time-adapters.md`.
- Settings bootstrap follows that same composition rule: `platform/settings.desktop.ts` delegates to typed IPC, `platform/settings.browser.ts` validates browser app-data against generated Rust defaults/catalogs, and each `platform/*.ts` entry installs its adapter into the platform-neutral Settings Projection before rendering. Keep concrete storage imports out of `app/settings/projection.ts`.
- Both HTML entries own the tiny guarded `canopi-theme` cache read that sets `<html data-theme>` before module loading and first paint. `utils/theme.ts` then owns reactive DOM/cache synchronization for the active module lifetime; components and browser settings adapters must not duplicate it.
- Web Edition v1 is not offline-first. Do not add service workers, PWA install prompts, app-managed precache logic, or offline map/image promises to the browser shell without a later decision. See `docs/adr/0022-web-edition-not-offline-first.md`.


## Browser App Data

- `web/browser-app-data.ts` owns the synchronous caller API, resource schemas, and normalization for four independently versioned localStorage records: Drafts, Settings, Species activity, and Saved Object Stamps. Callers must not depend on keys, migration progress, or the authority tombstone, and must not reconstruct the former v1 aggregate.
- `web/browser-partition-storage.ts` owns staged authority, quota reservation, cross-tab revalidation, and interrupted-finalization recovery. A valid v2 record immediately owns its resource. Missing or unsupported records read through v1 until all four supported records validate and a separate immutable completion tombstone commits; only then may v1 be removed. Corrupt or foreign v2 records must not erase recoverable legacy data.
- Migration happens on resource writes, not through an eager full-store copy. Reads do not duplicate v1. A write reserves marker quota before publishing its target record; if publication fails for quota while v1 still owns that resource, the write may remain live through v1. A later store instance retries interrupted finalization, and stale progress cannot overwrite the completion tombstone.
- Ordinary v2 Settings, Species, and Stamp writes do not parse or serialize Draft bodies. A resource's first transition or quota fallback may touch the aggregate. Concurrent writes to the same resource remain last-writer-wins; an old client may recreate v1, but cannot supersede valid v2 resources and is ignored entirely after the tombstone commits.
- The compile-time browser settings adapter loads and saves the complete shared `Settings` contract through this store. `WebApp` owns the browser Design Session autosave observer. Shell and Canvas settings commands mutate `app/settings/projection.ts` rather than importing storage or receiving persistence callbacks.
