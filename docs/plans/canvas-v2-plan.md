## 1. Rules for every phase

**Decisions of 2026-10-01.** The user agreed the scope of the value audit of `b69bec4d` (its synthesis and roadmap check). Every decision is listed here once, with where it is applied:

- **U1. One release.** Phase 0, F, 1, 2, 3 and R ship together as 2.0; nothing is released between phases. No interim "before phase N" behaviour is built. The per-phase release tasks (gallery screenshots, the docs check against the code, release notes, a Playwright scenario per phase beyond those that guard the refactor) run once, at the release close (section 4). Each reviewed step is still pushed.
- **U2. No pan with a second button during a left drag.** The nested "drag inside a drag" mode, its two-level Esc, fixtures A11b, A12 and A12b and its live step are gone; A11 stays as one fixture, rewritten by the phase that changes its outcome (spec §2.2, §5.1; ADR 0017). Wheel zoom and key navigation during a drag stay.
- **U3. One map angle for the whole PDF layout**: the bearing captured when the PDF workspace opens under As on screen, 0 under North up. No per-area angle, no turned page-window outlines on the overview, no corner fit (spec §4.12; ADR 0015). It changes no stored format: the layout angle is held in memory only (user, 2026-10-01).
- **U4. No edge highlight** for "Turn view to this edge"; 0B-5 deletes the declared hook (`interaction-ports.ts:84`).
- **U5. A panel drag over the map hides the armed tool's preview**: 0B-4 keeps spec §1.4 "Drops" ("any dragover hides the active tool's draft").
- **U6. The new mouse and pen feel lands in F**, not phase 2: the hover ends cleanly over owned chrome, the text entry and handles. F rewrites the LEGACY input-feel fixtures instead of carrying them to phase 2. F adds a 3 px mouse and pen drag threshold (section 8).
- **U7. 0C folds into F.** Keys, Esc, focus and arming are not rebuilt in today's form: F builds the key router, the Esc layers, the focus owner and `armCanvasTool` once, in their target form (section 4, F). The three 0C hand-off items 0D2 needs are a small hand-off commit before 0D2.
- **U8. LiDAR's Return to Design keeps the exact view** (exception 3 below; the 0E trim).
- **The audit.** Its section 1 (cuts in the unbuilt plan) is applied in sections 4 and 5 and the spec; its section 2 (cuts in landed code) is step 0B-5 Cleanup; its section 3 (cuts later) is in 0E, R, the phase-0 close and the release close; its section 5 is "Checked and kept" below.

**How a step is chosen.** These rules come from the audit and apply to every step from 0B-4 on (AGENTS.md, "Working method"):
- Before a step is built, its brief names the user path or roadmap item behind each planned behaviour; a behaviour with none is dropped, and the drop is named in the handoff.
- A refactor keeps what users see, not internal mechanisms: a guard, counter, fallback or exact-number test stays only when a user path needs it.
- Nothing is built that a later step of this release replaces (U1).
- The old path goes in the change that replaces it; two paths never run side by side.
- Streams run in parallel only on areas that share no file; coupled work is one sequential stream.
- The spec states contracts and user-visible rules; line numbers belong in briefs. The line numbers already in these documents are hints: each brief re-greps them at its entry HEAD.

**Refactor first, behaviour unchanged.** Phase 0 changes structure only. It runs at bearing 0 under `LEGACY_BINDINGS`; every behavioural test passes with only mechanical harness edits (the named rewrites in section 4 are the only exceptions, each in the counting guard); the reference screenshots are the pixel evidence (native: section 3.1; Web: the committed baselines of section 3.2). `__tests__/pixi-scene.test.ts` mocks `pixi.js` and asserts draw calls, not pixels, and is one of 0D2's named rewrites. Anything else a user could notice waits for phase F or later, in its own commit with a regression test written first. A phase-0 commit that needs a behaviour change to go green is wrong: stop and apply the next rule.

Four named exceptions ship in phase 0, each in its own commit with its regression test written first: the first two follow from the architecture itself and ship in 0B; the third is 0E's cut to the camera behaviour users need; the fourth is a bug fix in 0B-5:

1. **Drag starts are world points, and the host re-emits the live gesture on a camera frame**, so a drag, a draft and a placement preview stay on the ground under a still pointer through a wheel, key or button zoom or pan (ADR 0018; canopi-f47t.2's "no drift" item). Today a drag start stays on the screen and the Place plants ghost, the stamp ghosts, the Plant a row endpoint and the new-note text entry keep their old place until the pointer moves; the re-emit also refreshes the hover restyle and tooltip under the still pointer and re-culls a draft's chips at the new scale; with the pointer off the map (a key or button zoom) the host calls the tool's `viewChanged` instead, so the chips re-cull on every frame, as today (spec §1.4). Tests: `tools/tool-host.test.ts` "a drag start stays on the ground through a wheel zoom", "a hover is re-emitted on a camera frame, so a placement preview stays under a still pointer" and "a camera frame with the pointer off the map calls viewChanged"; named rewrite: the plants split's "refreshes Plant Spacing preview after viewport changes" wheels at the pointer, where both behaviours agree (D3). Without navigation under a still pointer nothing differs.
2. **Drafts draw in Pixi** (ADR 0019; today they are DOM boxes, `interaction/overlay-ui.ts:32-72`). Equivalence: the same colour tokens, stroke widths and dash patterns; the DOM `box-shadow` casing (`DRAFT_LINE_CASING`) becomes a Pixi casing stroke of the same colour and width under the line; rectangle and ellipse drafts are world shapes instead of CSS-rotated boxes; labels keep today's chips (spec §1.4, label tones) and Plant a row's ghosts their discs (`GhostEntity` mark `'dot'`); named by-eye deviations remain: polygon vertex markers are `circle-px` `{ radiusPx: 1.75, widthPx: 3.5 }` with the `draft` token (a light disc of radius 3.5 px with a 1 px casing ring, against today's 2.75 px core with a 1.5 px ring), and the band's casing keeps the +2 rule (4 px against today's 5 px); Plant a row's guide has a dashed casing (today a solid casing under a dashed line), the guide and the source ring draw under the row discs (today over them), and the ring sits at the presented radius (today a 2 px border inset in the plant's bounds box); drafts sit in the scene, on top of the scene's content (plants, notes and labels included, as today) and under every piece of DOM chrome (today some previews sit over the handle layer). Test: `renderers/draft-layer.test.ts` plus each tool's `recordingRenderer.lastDraft()` assertions. The live check compares drafts by eye, not by pixels (section 4, phase 0, step 5).
3. **The camera keeps only what users need** (decision 2026-10-01; section 4, 0E). `runtime.init` fits where today's start frame placed 100 m across the shorter screen side: the Design fit, or the new-Design overview for an empty or not yet loaded Design (`fit.ts`, `emptySceneScale`). A Design opened from the no-Design state is loaded before init, so its first frame on a map is the Design fit, which also removes a likely 100 m close-up between two fits (inferred from the code, not seen), and the fit is taken before plant labels load, as every other open already takes it. A Design opened from the start screen loads after init (`lifecycle.ts` awaits `runtime.start()`, whose activation runs `runtime.init`, before `startAttachedDesignSession` loads): init shows the empty overview at the pre-load plane, where today it shows the 100 m frame, and the Design's fit is the one its load takes, unchanged. LiDAR's Fit to data keeps one bookmark, the view before the first unreturned fit: a later fit on another layer keeps it, so either layer's Return to Design lands on the view before the first fit, never on a layer's coverage, and any manual navigation (pan, zoom, turn, the zoom buttons, Fit to Design, Return to Design) or jump drops it, so a fit followed by the user moving elsewhere returns to the whole Design, never to a stale view (today a leftover bookmark returns to an older view); the plant finder's Zoom to them sets none (today it leaves one that a later Return to Design lands on); LiDAR's Return to Design with no bookmark left (after a place search, story step or saved view) frames the Design (today it does nothing while its button flips back). Tests: `scene-runtime.test.ts` "init frames a Design opened before it: the first frame is the fit, with no 100 m frame between two fits" and "a Design loaded after init: the last frame before its first scene render is the load's fit", `view/navigation.test.ts` "a return lands before the first focus, whatever frameBounds did in between" and "manual navigation and Fit to Design drop the bookmark", and `__tests__/lidar-camera-navigation.test.ts` "Return to Design without a bookmark frames the Design" and "a pan after Fit to data drops the bookmark: Return to Design frames the Design". Without a LiDAR fit, a plant-finder zoom or a Design open nothing differs; a start-screen open differs only in the frame shown before the load's fit.
4. **In overview a release elsewhere in the app reaches the page** (0B-5, item 1). Today, in overview, every pointerup with no canvas session, anywhere in the app, is prevented and stopped by a window capture listener (`input/recognise.ts:236-241`), so panel sliders and drag handles do not end their drags. Tests: `input/recognise.test.ts` "in overview a pointerup with no session passes untouched" and `input/dom-input-source.test.ts` "an overview pointerup elsewhere still reaches the page". Outside overview nothing differs.

Three 0B-5 items change what happens only after an internal fault (a cancellation, a sink or a tool activation that throws), each with its test written first: section 4, 0B-5, items 2, 4 and 15; section 8 names them.

**Keys, Esc, focus and arming are built once, in F** (U7). Phase 0 keeps 0B's keyboard port, fed by the source's `legacyKeys`, with today's behaviour, and builds no legacy key router, Esc chain or arming path. F builds them in their target form, one row per commit, each test first, under three conditions: the popover Esc row lands in the same window as the Esc chain (otherwise one Esc closes a popover and clears the selection, fixture I8); the `SiteOnboarding.tsx` edit follows the canopi-f47t.6.1 (28w8 part 3) commit; `FocusReason 'drop'` stays.

**By-eye conventions (0D2).** Three effects of the coarse view signals ship in 0D2 as conventions, named in its handoff (section 8) and compared by eye, never pixel-matched: (1) the scale ratio, the scale bar and the zoom reached by the scale menu and by "Zoom in to see names" read `ViewReadSurface.groundMetresPerPixel`, three significant figures at the screen centre: the ratio can read one rounding step off when the true value lies within 0.5 % of a boundary (a true 1:144.9 reads 1:150, today 1:140), the bar can move 1 px, those zooms land within 0.5 % of today's, and with no map attached the ground resolution is MapLibre's at the centre latitude instead of `1 / px per m`, under 0.2 % apart; (2) the overview pin is `designPin`, whole pixels: up to 0.5 px from today's; (3) the labels count ("Names shown for 70 of 282 plants in view") re-reads on the settled frame (150 ms after the last camera change, a resize included) and on a zoom-band change, not live during a pan or zoom, since P10 keeps per-frame reads out of `app/`. Label admission itself keeps today's cadence until phase R.

Everything else a user could notice (the GeoLibre selection-drag guard, the Windows HTML5-drop fix) waits for phase F.

**Stop and amend.** If building shows that the design is wrong (an interface cannot carry a case, a MapLibre assumption fails, a policy cannot be written, a step cannot ship with its gates green), the agent stops, does not work around it, and reports to the main agent. The main agent amends the ADR and the spec in one docs commit, says what changed and why, and tells the user before work resumes. A change to the `.canopi` format or the user's local data (user DB, settings, LiDAR catalogue) may be made when it improves the project (user, 2026-10-02), without a migration (ADR 0021: older files are refused, older local data moved aside), and is named in the handoff; the plant catalog (`canopi-core.db`) never changes. Under the user's standing permission (2026-09-28) a process rule in AGENTS.md or a guide that blocks a better fix is rewritten in the same change and named in the handoff.

**Tests.** A bug fix carries a regression test written first. A test is deleted only in the commit that adds its replacement, or that retires it with the reason no user sees what it checked (`{ "retired": "<why>" }` in the counting guard's map, section 3.4); the bead records where each replacement lives. New camera and view tests compare numbers with `toBeCloseTo(…, 6)`, never exact goldens. The counting guard (`desktop/web/scripts/count-vitest-tests.mjs`, section 3.4) runs at the end of every phase-0 sub-phase.

**Gates.** Every sub-phase ends with the frontend gates green on the branch: `cd desktop/web && npx tsc --noEmit && npx vitest run --maxWorkers=4 && npm run test:coverage -- --maxWorkers=4 && npm run check:ui && npm run build && npm run build:web`. Phases 1 and 2 add the Rust and shared-contract gates (phase 1: `LastView.bearing`; phase 2: the `settings.rs` doc comments, which `bindings-gen` copies into `generated/contracts.ts`, committed regenerated with the change) (`cargo fmt --all -- --check`, `CANOPI_SKIP_BUNDLED_DB=1 cargo clippy --workspace --all-targets -- -D warnings`, `CANOPI_SKIP_BUNDLED_DB=1 cargo test --workspace`, `cargo cov` above its floor, `npm run gen:types && npm run check:types`). Docs commits run `python3 scripts/check_docs.py`. No performance gates (user); phase R records measurements in its bead as evidence only.

**Worktrees and disk.** Agents work in worktrees under `.rq-scratch/` with `CARGO_TARGET_DIR=/home/daylon/projects/canopi/.rq-scratch/shared-build/target`. The main agent runs `df -h /` before launching agents and cleans up below about 50 GB free. Merged worktrees and their caches (`/tmp/canopi-*`, headless browser profiles) are removed; screenshots are kept. Review profiles are not caches: they live under `.rq-scratch/reference/<phase>/` and go when the phase's bead closes (section 3.1, step 6).

**Ownership.** One file has one owner per sub-phase (tables below). The main agent owns `__tests__/frontend-architecture-policies.test.ts`, `__tests__/canvas-boundaries.test.ts`, the seams, the test split and counting guard, locale integration, every `bd` write and the worktree's `.beads/issues.jsonl` (section 7, "JSONL"), the Playwright scenarios (phase 0's and the release close's, after canopi-9x95) and every end-of-sub-phase deletion. In the 11 locale files (`i18n/*.json`) an agent adds or removes only its own keys. Nobody edits a file outside their list; a needed edit elsewhere goes to the main agent.

**Stored data.** The only stored-format change in this plan is `LastView.bearing` in settings (phase 1, `#[serde(default)]`, 0): a one-line default the user approved; no migration step. The second approved change, the optional `PdfPrintArea.rotationDeg`, is dropped with the per-area angle (U3); PDF setups are not stored (`app/canvas-pdf/types.ts:18-28` at `b69bec4d`), so the one layout angle is held in memory only (decided with the user, 2026-10-01; no stored-data question remains). `.canopi`, the user DB and the LiDAR catalogue change only where a step shows it improves the project (stop and amend, above); the plant catalog never changes.

**Core exit.** Every phase from phase 0 on (phase 0 as a whole, F, 1, 2, 3 and R) exits with, besides its own Exit bullets: every test named in its section green; its policies green; the strings of its spec §9 table in 11 locales (none for phase 0 and R); its live check recorded in the bead; the Chromium and WebKit job (`base.spec.ts`, `phase-0-refactor.spec.ts`) green on the pushed commit; the pre-push review recorded. The docs check against the code, the gallery entries, the release notes and the 2.0 Web scenario run once, at the release close (U1); each phase bead lists its entries for them. Section 7 copies the core exit into every phase bead's acceptance.

**Conventions.** Where the spec marks a rule "(convention)", the planner chose it; the handoff of the phase that ships it names it so the user can overturn it (section 8).

## 3. Common procedures

### 3.1 Live check on an isolated review instance

Run from the integration worktree after the phase's gates pass. Never drive the user's own app.

1. Note what already listens: `ss -ltnp | grep -E ':(1420|1431|922[0-9])'`. The user's own `cargo tauri dev` usually holds 1420 and 9223; leave it running and never drive it. If port 1431 is taken by something other than an earlier review instance of yours, stop and ask.
2. Make a profile: `R=/home/daylon/projects/canopi/.rq-scratch/reference/<phase>; mkdir -p $R/{config,data,cache}` (`<phase>` is the phase, not the sub-phase: `phase-0` for all of 0A–0E, `28w8` for the 28w8 checks). It lives under the git-ignored `.rq-scratch/` (`.gitignore:67`), never under `/tmp`, so neither a reboot nor the `/tmp/canopi-*` cache cleanup of section 1 removes the references that later sub-phases compare against; `cp /home/daylon/projects/canopi/.rq-scratch/reference/orchard.canopi $R/orchard.canopi`, plus one empty new Design. Autosave writes into that copy, so restore it from the master (`cp` again) before each comparison. The reference orchard (`.canopi` format v9, 2,200 plants, 24 zones, 106 notes) is a git-ignored, read-only master: copy it into each review profile and never open the master itself in the app. `/home/daylon/projects/canopi/.tmp/dense-canvas-review/orchard.canopi` is not it (format v5, refused: Canopi 2.0 opens only v9). Never pick a Design from `~/Downloads` or the app's data folders.
3. Launch the review instance from the worktree's `desktop/` directory, with its own identifier (so the single-instance plugin does not hand off to the user's app) and its own Vite port:
   `XDG_CONFIG_HOME=$R/config XDG_DATA_HOME=$R/data XDG_CACHE_HOME=$R/cache CARGO_TARGET_DIR=/home/daylon/projects/canopi/.rq-scratch/shared-build/target cargo tauri dev -f mcp-bridge --config '{"identifier":"com.canopi.review","build":{"devUrl":"http://localhost:1431","beforeDevCommand":{"script":"npx vite --port 1431 --strictPort","cwd":"web"}}}'`
4. Find the bridge port (9223, or the next free one when the user's instance holds 9223) and check its owner: `ss -ltnp` must show the process launched in step 3 (check `/proc/<pid>/exe` and its working directory). Start the MCP driver session on that port.
5. Drive with `webview_interact` (click, double-click, right-click, hover), `webview_keyboard` (press, down, up with modifiers; Space is `"Space"`, since `" "` sends the code `" "`), `webview_screenshot` and `webview_execute_js`. `webview_interact scroll` does not reach the canvas: a wheel is a `WheelEvent` dispatched on the map host through `webview_execute_js`. The bridge has no button-specific drags: drags are dispatched as `PointerEvent` sequences on the map host (`[aria-label="Design map"]`) through `webview_execute_js`, split into separate calls (press, moves, release). They exercise the pipeline, not WebKitGTK's native event order; the native order is covered by the recogniser fixtures and the Playwright job, and the handoff says which was driven.
6. Keep screenshots under `$R/shots/` (the pre-phase references under `$R/shots/reference/`). Remove `$R` only when the phase's bead closes (for phase 0, the commit that closes canopi-f47t.5 after 0E), never when a sub-phase or worktree merges; screenshots are kept (move `$R/shots/` to `/home/daylon/projects/canopi/.rq-scratch/screenshots/<phase>/` and delete the rest of `$R`).

Reference screenshots for "unchanged" checks are taken with the same profile, Design, window size and camera on the commit before the phase. For phase 0 that is the 28w8 fix commit or any later commit before 0A's first commit: the seams commit (types and a test split) and canopi-9x95 (dev dependency, e2e files, CI job, `test.exclude`) change no runtime code, so their pixels are the same. ### 3.4 The counting guard

`desktop/web/scripts/count-vitest-tests.mjs` (seams commit, main agent) proves that no test was lost while phase 0 moves and replaces tests. - **Collect.** It runs `npx vitest list --json=<tmp file>` in `desktop/web` (vitest 4.1: `list` writes JSON only with `--json`; `--reporter` does not change its output) and reads each test's file and full name (describe path plus title). - **Record mode (once, seams commit).** `node scripts/count-vitest-tests.mjs --record` writes the baseline. It builds the file list by importing `src/__tests__/support/architecture/source-facts.ts` directly: Node ≥ 22.18 strips types by default and that file imports only `typescript`, so `discoverTypeScriptSourceGraph(new URL('../src/', import.meta.url), 'src')` works from an `.mjs` (checked with Node 22.22.0 on 2026-09-29). The script checks `process.versions.node` first and stops below 22.18 with a message naming that version; `engines` in `package.json` stays `^22.13.0` (CI never runs the script, and `package.json` belongs to canopi-9x95 in the seams window). `policy-harness.ts` cannot be imported this way (extensionless relative imports) and is not needed. The check mode never builds the graph: it compares `vitest list` with the committed baseline and map only.
- **Baseline.** `canvas-v2-test-baseline.json`, committed in the seams commit *before* the split: every test of every baseline file, as `{ file, name }` with `it.each` rows expanded as `vitest list` reports them, and N recorded per file.   1. a baseline module: the modules phase 0 moves, deletes or re-types (spec §1.9, the moves and renames of section 4, and the modules whose exported types change: `renderers/scene-types.ts`, `scene/types.ts`, `canvas/projection.ts`, `canvas/runtime/camera.ts`, `canvas/inspection.ts`);

  3. a file under `__tests__/support/` that itself matches 1 or 2 (one hop, for example `__tests__/support/canvas-query-surface.ts`).

  4. **Source readers.** A test that never imports a baseline module but reads one's source with `readFileSync`, a `readSource`-style helper or a path list is invisible to rules 1–3 (at `0f05d927` `__tests__/scene-interaction-tool-boundary.test.ts` imports only `node:fs` and `vitest`). These files sit in `EXTRA_BASELINE_FILES`, a reviewed constant in the script beside the baseline-module constant, seeded with the tool-boundary test. The script does not parse `readFileSync` arguments (they are built from template strings and path lists). Instead record mode prints every test file that rules 1–3 did not select but whose text contains a baseline module's path without its extension (relative to `src/`, for example `canvas/runtime/scene-interaction`). - **Rule.** Names are counted, not just matched: for each full name, the current list (any file) holds at least as many tests as the baseline, less those mapped to a replacement that is present (or retired, or to a policy that exists: `{ policy: "<name>" }` is present when `__tests__/frontend-architecture-policies.test.ts` or `__tests__/canvas-boundaries.test.ts` contains that exact string as a string literal; AST policies run inside one test, so `vitest list` cannot show them, and a renamed policy fails the guard until the map follows it), so two tests with one name cannot hide a lost one. A module in doubt goes in. ## 5. Policy tests

Every new policy rule's `name` (the AST policy's `name`, the regex policy's `it` title in `canvas-boundaries.test.ts`) starts with its P-id and a space, then says what that rule checks, for example `'P5 tools import no MapLibre, DOM or Pixi'`; a row with several rules (P5's `forbid-imports` and `confine-symbols`) gives each its own unique name under the same P-id. The table's Name column titles the row, not the string. The counting guard's map references these exact strings (section 3.4); existing policies keep their names. AST policies go in `__tests__/frontend-architecture-policies.test.ts` with the existing kinds (`__tests__/support/architecture/policy-harness.ts`); each gets a planted-graph negative test in the pattern of that file. `forbid-source-symbols` has no `exceptFrom`, so a symbol rule with exempt files is written as `confine-symbols` (`from` the area, `allowedFrom` the exempt files plus tests). `forbid-source-symbols` and `confine-symbols` match every identifier (`__tests__/support/architecture/source-facts.ts:108`), so confined names must be distinctive. `forbid-calls` compares `targets` globs with the full callee text (`attachment.map.jumpTo`), and records `property` only for member calls, so a bare call (`selectCanvasTool('polygon')`) is caught by `confine-symbols`, not by `properties`. Regex policies go in a new `__tests__/canvas-boundaries.test.ts`, which walks every `.ts`/`.tsx` file under `src/` (as `frontend-architecture-policies.test.ts:2121` does with `readdirSync`), skips tests, applies each regex to every file and compares the hits against the policy's named allowlist; each regex has one planted-file negative test, so a coupling reintroduced in a new file fails. Before an allowlist is written, its bead records the inventory counts, so every allowlist entry is named, with its count and the phase that removes it.
