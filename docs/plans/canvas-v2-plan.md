## 1. Rules for every phase

**Decisions of 2026-10-01.** The user agreed the scope of the value audit of `b69bec4d` (its synthesis and roadmap check). Every decision is listed here once, with where it applies:

- **U1. One release.** Phase 0, F, 1, 2, 3 and R ship together as 2.0; nothing is released between phases. No interim "before phase N" behaviour is built. The per-phase release tasks (gallery screenshots, the docs check against the code, release notes, a Playwright scenario per phase beyond those that guard the refactor) run once, at the release close (section 4). Each reviewed step is still pushed.
- **U2. No pan with a second button during a left drag.** The nested "drag inside a drag" mode, its two-level Esc, fixtures A11b, A12 and A12b and its live step are gone; A11 stays as one fixture, rewritten by the phase that changes its outcome (spec §2.2, §5.1; ADR 0017). Wheel zoom and key navigation during a drag stay.
- **U3. One map angle for the whole PDF layout**: the bearing captured when the PDF workspace opens under As on screen, 0 under North up. No per-area angle, no turned page-window outlines on the overview, no corner fit (spec §4.12; ADR 0015). It changes no stored format: the layout angle is held in memory only (user, 2026-10-01).
- **U4. No edge highlight** for "Turn view to this edge" (the declared hook is gone).
- **U5. A panel drag over the map hides the armed tool's preview** (spec §1.4 "Drops": "any dragover hides the active tool's draft").

- **U7. 0C folds into F.** Keys, Esc, focus and arming are not rebuilt in today's form: F builds the key router, the Esc layers, the focus owner and `armCanvasTool` once, in their target form (section 4, F).
- **U8. LiDAR's Return to Design keeps the exact view** (phase 0's exception 3, section 4).
- **The audit.** Its section 1 (cuts in the unbuilt plan) is applied in sections 4 and 5 and the spec; its sections 2 and 3 (cuts in landed code) were done in phase 0, except the items section 4 lists as left, phase R's and the release close's; its section 5 is "Checked and kept" below.

**How a step is chosen.** These rules come from the audit and apply to every step (AGENTS.md, "Working method"):
- Before a step is built, its brief names the user path or roadmap item behind each planned behaviour; a behaviour with none is dropped, and the drop is named in the handoff.
- A refactor keeps what users see, not internal mechanisms: a guard, counter, fallback or exact-number test stays only when a user path needs it.
- Nothing is built that a later step of this release replaces (U1).
- The old path goes in the change that replaces it; two paths never run side by side.
- Streams run in parallel only on areas that share no file; coupled work is one sequential stream.
- The spec states contracts and user-visible rules; line numbers belong in briefs. The line numbers already in these documents are hints: each brief re-greps them at its entry HEAD.

**Behaviour changes.** Phase 0 changed structure only, apart from four named exceptions; they are listed under "What phase 0 changed for users" in section 4 for the release notes (code comments cite them as "plan §1, exception N"). From F on, anything a user could notice lands in its own commit with its regression test written first, and the phase's handoff names it (section 8).

**Keys, Esc, focus and arming are built once, in F** (U7). Until then 0B's keyboard port, fed by the source's `legacyKeys`, keeps today's behaviour; there is no legacy key router, Esc chain or arming path. F builds them in their target form, one row per commit, each test first, under three conditions: the popover Esc row lands in the same window as the Esc chain (otherwise one Esc closes a popover and clears the selection, fixture I8); the `SiteOnboarding.tsx` edit follows the canopi-f47t.6.1 (28w8 part 3) commit; `FocusReason 'drop'` stays.

**By-eye conventions (shipped in phase 0).** Three effects of the coarse view signals are conventions the user may overturn, compared by eye, never pixel-matched: (1) the scale ratio, the scale bar and the zoom reached by the scale menu and by "Zoom in to see names" read `ViewReadSurface.groundMetresPerPixel`, three significant figures at the screen centre (the ratio can read one rounding step off within 0.5 % of a boundary; with no map attached the ground resolution is MapLibre's at the centre latitude, under 0.2 % from `1 / px per m`); (2) the overview pin is `designPin`, whole pixels; (3) the labels count re-reads on the settled frame (150 ms after the last camera change, a resize included) and on a zoom-band change, not live during a pan or zoom, since P10 keeps per-frame reads out of `app/`. Label admission keeps its cadence until phase R.

**Reviews (user, 2026-10-02).** One review round per step, by one reviewer whose findings are each verified before anyone fixes them. A second round runs in three cases: on the fix diff alone whenever a review's findings changed code (in phase 0 a fix brought a regression only that check caught); a full second round on work that touches the user's files or stored data, on phase 1's rotation core, and on any step whose first round found a blocker or a major finding; never more than two full rounds on one diff (a third points at the design or the tests). The pre-push review of everything since the last push stays.

**User decisions.** A decision the user made, recorded with its date, changes only when the user changes it. An agent that finds one in its way stops and reports it; reviews check that the docs still say what the user decided (phase 0: a merged rewrite reversed the user's stored-data permission until the review caught it).

**Stop and amend.** If building shows that the design is wrong (an interface cannot carry a case, a MapLibre assumption fails, a policy cannot be written, a step cannot ship with its gates green), the agent stops, does not work around it, and reports to the main agent. The main agent amends the ADR and the spec in one docs commit, says what changed and why, and tells the user before work resumes. The `.canopi` format and local data (the user DB, Drafts, Web storage, the LiDAR catalogue) may change when that improves the project, without asking the user first, and each change is named in the handoff (ADR 0021, "Later format changes"; user, 2026-10-02); after 2.0 a format change decides between refusing older files and a migration case by case, with no ladder by default. A new settings field with a default is not a format change. The plant catalog (`canopi-core.db`) never changes. Under the user's standing permission (2026-09-28) a process rule in AGENTS.md or a guide that blocks a better fix is rewritten in the same change and named in the handoff.

**Tests.** A bug fix carries a regression test written first. A test is deleted only in the commit that adds its replacement, or that retires it with the reason no user sees what it checked, named in the commit; the bead records where each replacement lives. New camera and view tests compare numbers with `toBeCloseTo(…, 6)`, never exact goldens.

**Gates.** Every step ends with the frontend gates green on the branch: `cd desktop/web && npx tsc --noEmit && npx vitest run --maxWorkers=4 && npm run test:coverage -- --maxWorkers=4 && npm run check:ui && npm run build && npm run build:web`. Phases 1 and 2 add the Rust and shared-contract gates (phase 1: `LastView.bearing`; phase 2: the `settings.rs` doc comments, which `bindings-gen` copies into `generated/contracts.ts`, committed regenerated with the change) (`cargo fmt --all -- --check`, `CANOPI_SKIP_BUNDLED_DB=1 cargo clippy --workspace --all-targets -- -D warnings`, `CANOPI_SKIP_BUNDLED_DB=1 cargo test --workspace`, `cargo cov` above its floor, `npm run gen:types && npm run check:types`). Docs commits run `python3 scripts/check_docs.py`. No performance gates (user); phase R records measurements in its bead as evidence only.

**Worktrees and disk.** Agents work in worktrees under `.rq-scratch/` with `CARGO_TARGET_DIR=/home/daylon/projects/canopi/.rq-scratch/shared-build/target`. The main agent runs `df -h /` before launching agents and cleans up below about 50 GB free. Merged worktrees and their caches (`/tmp/canopi-*`, headless browser profiles) are removed; screenshots are kept. Review profiles are not caches: they live under `.rq-scratch/reference/<phase>/` and go when the phase's bead closes (section 3.1, step 6).

**Ownership.** One file has one owner per sub-phase (tables below). The main agent owns `__tests__/frontend-architecture-policies.test.ts`, `__tests__/canvas-boundaries.test.ts`, `__tests__/unused-code.test.ts` with its snapshot, locale integration, every `bd` write and the worktree's `.beads/issues.jsonl` (section 7, "JSONL"), the Playwright scenarios (`desktop/web/e2e/**`) and every end-of-phase deletion. In the 11 locale files (`i18n/*.json`) an agent adds or removes only its own keys. Nobody edits a file outside their list; a needed edit elsewhere goes to the main agent.

**Stored data** (ADR 0021). Canopi 2.0 opens only the current `.canopi` version and moves older local data aside; there are no migration ladders. The plan's one stored change is `LastView.bearing` in settings (phase 1, `#[serde(default)]`, 0): a defaulted settings field, which ADR 0021 keeps outside migrations, approved by the user. The per-area `PdfPrintArea.rotationDeg` is dropped with the per-area angle (U3); PDF setups are not stored, so the one layout angle is held in memory only (user, 2026-10-01). Any other stored-format change may be made when it improves the project and is named in the handoff (stop and amend, above); the plant catalog never changes.

**Core exit.** Every remaining phase (F, 1, 2, 3 and R) exits with, besides its own Exit bullets: every test named in its section green; its policies green; the strings of its spec §9 table in 11 locales (none for R); its live check recorded in the bead; the Chromium and WebKit job (`base.spec.ts`, `phase-0-refactor.spec.ts`) green on the pushed commit; the pre-push review recorded; the unused-code check run (section 4, "Unused-code check"). The docs check against the code, the gallery entries, the release notes and the 2.0 Web scenario run once, at the release close (U1); each phase bead lists its entries for them. Section 7 copies the core exit into every phase bead's acceptance.

**Conventions.** Where the spec marks a rule "(convention)", the planner chose it; the handoff of the phase that ships it names it so the user can overturn it (section 8).

## 2. Order

```
phase 0 (done) ─▶ F (done) ─▶ 1 ─▶ 2 ─▶ 3 ─▶ 2.0 release close
                  R: between F, 1, 2 and 3
                  2.0 bug fixes: between canvas phases, from F on
```

- F needs the phase-0 bead closed; phase 1 needs F, 2 needs 1, 3 needs 2; the release close needs 3, R and the 2.0 bug fixes.
- R's files (`renderers/**`, `chrome/**`, `tools/select/move-drag.ts`, `scene-runtime/{drag-state,selection}.ts`) overlap F (the note editor's IME row), phase 1 (the Renderer's layers, Select) and phase 3 (the handle layer), so R is not a parallel stream: each R sub-phase lands between two phases, never while one is open.
- Every step ends with the gates green on the branch and is pushed after its review. Nothing is released before the release close (U1); no phase is a release candidate on its own.

## 3. Common procedures

### 3.1 Live check on an isolated review instance

Run after the phase's gates pass, from a worktree no other agent edits during the check (`git worktree add --detach .rq-scratch/canvas-v2-live <commit>`, removed afterwards): the review instance's Vite hot-reloads any edit, so a fix written in the same worktree changes the code under test mid-check (phase 0, 0E). Never drive the user's own app.

1. Note what already listens: `ss -ltnp | grep -E ':(1420|1431|922[0-9])'`. The user's own `cargo tauri dev` usually holds 1420 and 9223; leave it running and never drive it. If port 1431 is taken by something other than an earlier review instance of yours, stop and ask.
2. Make a profile: `R=/home/daylon/projects/canopi/.rq-scratch/reference/<phase>; mkdir -p $R/{config,data,cache}` (`<phase>` is the phase: `phase-F`, `phase-1`, …). It lives under the git-ignored `.rq-scratch/` (`.gitignore:67`), never under `/tmp`, so neither a reboot nor the `/tmp/canopi-*` cache cleanup of section 1 removes the references a phase compares against; `cp /home/daylon/projects/canopi/.rq-scratch/reference/orchard.canopi $R/orchard.canopi`, plus one empty new Design. Autosave writes into that copy, so restore it from the master (`cp` again) before each comparison. The reference orchard (`.canopi` format v9, 2,200 plants, 24 zones, 106 notes) is a git-ignored, read-only master: copy it into each review profile and never open the master itself in the app. `/home/daylon/projects/canopi/.tmp/dense-canvas-review/orchard.canopi` is not it (format v5, refused: Canopi 2.0 opens only v9). Never pick a Design from `~/Downloads` or the app's data folders.
3. Launch the review instance from the worktree's `desktop/` directory, with its own identifier (so the single-instance plugin does not hand off to the user's app) and its own Vite port:
   `XDG_CONFIG_HOME=$R/config XDG_DATA_HOME=$R/data XDG_CACHE_HOME=$R/cache CARGO_TARGET_DIR=/home/daylon/projects/canopi/.rq-scratch/shared-build/target cargo tauri dev -f mcp-bridge --config '{"identifier":"com.canopi.review","build":{"devUrl":"http://localhost:1431","beforeDevCommand":{"script":"npx vite --port 1431 --strictPort","cwd":"web"}}}'`
4. Find the bridge port (9223, or the next free one when the user's instance holds 9223) and check its owner: `ss -ltnp` must show the process launched in step 3 (check `/proc/<pid>/exe` and its working directory). Start the MCP driver session on that port.
5. Drive with `webview_interact` (click, double-click, right-click, hover), `webview_keyboard` (press, down, up with modifiers; Space is `"Space"`, since `" "` sends the code `" "`), `webview_screenshot` and `webview_execute_js`. `webview_interact scroll` does not reach the canvas: a wheel is a `WheelEvent` dispatched on the map host through `webview_execute_js`. The bridge has no button-specific drags: drags are dispatched as `PointerEvent` sequences on the map host (`[aria-label="Design map"]`) through `webview_execute_js`, split into separate calls (press, moves, release). They exercise the pipeline, not WebKitGTK's native event order; the native order is covered by the recogniser fixtures and the Playwright job, and the handoff says which was driven.
6. Keep screenshots under `$R/shots/` (the pre-phase references under `$R/shots/reference/`). Remove `$R` only when the phase's bead closes, never when a step or worktree merges; screenshots are kept (move `$R/shots/` to `/home/daylon/projects/canopi/.rq-scratch/screenshots/<phase>/` and delete the rest of `$R`).

Reference screenshots for "unchanged" checks are taken with the same profile, Design, window size and camera on the commit before the phase. The basemap is hidden in the review profile before they are taken (Map layers, Basemap off: `basemap_visible` is a device setting stored in the profile's user DB, so it stays off for every later comparison), because OpenFreeMap tiles load over the network and change on their own.

### 3.2 Web Edition checks (Chromium and WebKit)

Every merge that touches the renderer, the camera or the map runs this check before the push, not only at a phase's end: in phase 0 it alone caught a crash of the real renderer (Pixi filters never registered) that unit tests with a recording renderer could not see.

The CI job `.github/workflows/web-edition-browsers.yml` (canopi-9x95) serves the built Web Edition (`npx vite preview --mode web --port 4174 --strictPort`, base URL `http://localhost:4174/app/web.html`) and runs `npx playwright test e2e/canvas --project=chromium --project=webkit` on every push, in the image `mcr.microsoft.com/playwright:v1.63.0-noble`, whose tag matches the exact `@playwright/test` pin in `desktop/web/package.json`. Its scenarios are `desktop/web/e2e/canvas/base.spec.ts` (open the base fixture, pan, zoom, Present, PDF) and `phase-0-refactor.spec.ts` (phase 0's live-check steps 2–6 and a viewport resize), on the committed fixture `desktop/web/e2e/fixtures/canvas-base.canopi`; the release close adds `v2.spec.ts` (U1). Rules that stay:

- **Network.** Every spec imports `test` from `desktop/web/e2e/support/offline.ts`, which aborts every request whose origin is not the preview server, so the default OpenFreeMap basemap never installs and baselines do not follow the tiles; a spec that fails on console errors allows exactly "Map basemap style failed to load:".
- **Baselines.** `toHaveScreenshot` baselines are recorded only in that image, never with the host's browsers: from the worktree root, after `npm run build:web` and `df -h /`, `docker run --rm --ipc=host -v "$PWD":/work -w /work/desktop/web --user $(id -u):$(id -g) -e HOME=/tmp mcr.microsoft.com/playwright:v1.63.0-noble npx playwright test e2e/canvas --update-snapshots`; if Docker fails, the job's `workflow_dispatch` input `update_snapshots` uploads them as an artifact. Screenshots are taken on settled states only.
- **Fixture.** `canvas-base.canopi` carries the build's `CURRENT_CANOPI_FILE_VERSION`; a format change re-saves it in the same commit. The orchard never enters CI; orchard-scale evidence is recorded by hand.
- **Version.** A Playwright bump is its own commit, with the image tag and the re-recorded baselines.
- **By hand.** `cd desktop/web && npx playwright install chromium`, `npm run build:web`, then `npx playwright test e2e/canvas --project=chromium`. WebKit runs locally only in the image, never with `sudo` (this host lacks `libavif16`).
- **Limits**, recorded in each bead: multi-touch is Chromium-only (CDP `Input.dispatchTouchEvent`); WebKit trackpad `gesture*` events cannot be produced natively and are covered by fixtures E9 and E10. Playwright's `page.mouse` sends real right and middle buttons, so the job is the standing evidence for the right-click order in Chromium (for WebView2) and WebKit (for WKWebView).

### 3.3 Inventory

Inventory rows have stable IDs by group: `INV-CAM` (camera and view transform), `INV-XF` (copies of the world-to-screen transform), `INV-TOOL` (tools, hit testing, snapping), `INV-REN` (rendering and per-frame work), `INV-ENT` (entanglement), `INV-LSN` (raw listeners), `INV-WR` (camera writers), `INV-KEY` and `INV-FOC` (keyboard and focus), `INV-DATA` (stored data), `INV-PDF` (PDF layout under a page angle), `INV-DOC` (docs, patterns, boards, locales) and `INV-TEST`. Each row's phase column names the work left, in this plan's phase names; `plan` rows are the documents the release close checks. A row is cleared when its fate (keep, change, delete) is done by the last phase its column names. The phase bead lists the row IDs it cleared, and a phase does not close with one of its rows open unless the inventory re-homes it to a later phase. Cleared rows are deleted from the inventory at each phase close.

Its last run, at the phase-0 close, counted a baseline of 2502 tests in 186 files: 2309 still present, 193 replaced or retired, none lost, 772 new. ## 5. Policy tests

Every new policy rule's `name` (the AST policy's `name`, the regex policy's `it` title in `canvas-boundaries.test.ts`) starts with its P-id and a space, then says what that rule checks, for example `'P5 tools import no MapLibre, DOM or Pixi'`; a row with several rules (P5's `forbid-imports` and `confine-symbols`) gives each its own unique name under the same P-id. The table's Name column titles the row, not the string. Existing policies keep their names. AST policies go in `__tests__/frontend-architecture-policies.test.ts` with the existing kinds (`__tests__/support/architecture/policy-harness.ts`); each gets a planted-graph negative test in the pattern of that file. `forbid-source-symbols` has no `exceptFrom`, so a symbol rule with exempt files is written as `confine-symbols` (`from` the area, `allowedFrom` the exempt files plus tests). `forbid-source-symbols` and `confine-symbols` match every identifier (`__tests__/support/architecture/source-facts.ts:108`), so confined names must be distinctive. `forbid-calls` compares `targets` globs with the full callee text (`attachment.map.jumpTo`), and records `property` only for member calls, so a bare call (`selectCanvasTool('polygon')`) is caught by `confine-symbols`, not by `properties`. Regex policies go in `__tests__/canvas-boundaries.test.ts`, which walks every `.ts`/`.tsx` file under `src/` (as `frontend-architecture-policies.test.ts:2121` does with `readdirSync`), skips tests, applies each regex to every file and compares the hits against the policy's named allowlist; each regex has one planted-file negative test, so a coupling reintroduced in a new file fails. Before an allowlist is written, its bead records the inventory counts, so every allowlist entry is named, with its count and the phase that removes it.
