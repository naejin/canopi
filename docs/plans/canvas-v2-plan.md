## 1. Rules for every phase

**Refactor first, behaviour unchanged.** Phase 0 changes structure only. It runs at bearing 0 under `LEGACY_BINDINGS`; every behavioural test passes with only mechanical harness edits (the named rewrites in section 4 are the only exceptions, each in the counting guard); the reference screenshots are the pixel evidence (native: section 3.1; Web: the committed baselines of section 3.2). `__tests__/pixi-scene.test.ts` mocks `pixi.js` and asserts draw calls, not pixels, and is one of 0D2's named rewrites. Anything a user could notice waits for phase F or later, in its own commit with a regression test written first. A phase-0 commit that needs a behaviour change to go green is wrong: stop and apply the next rule.

Two named exceptions follow from the architecture itself and ship in 0B, each in its own commit with its regression test written first:

1. **Drag starts are world points, and the host re-emits the live gesture on a camera frame**, so a drag, a draft and a placement preview stay on the ground under a still pointer through a wheel, key or button zoom or pan (ADR 0018; canopi-f47t.2's "no drift" item). Today a drag start stays on the screen and the Place plants ghost, the stamp ghosts, the Plant a row endpoint and the new-note text entry keep their old place until the pointer moves; the re-emit also refreshes the hover restyle and tooltip under the still pointer and re-culls a draft's chips at the new scale; with the pointer off the map (a key or button zoom) the host calls the tool's `viewChanged` instead, so the chips re-cull on every frame, as today (spec §1.4). Tests: `tools/tool-host.test.ts` "a drag start stays on the ground through a wheel zoom", "a hover is re-emitted on a camera frame, so a placement preview stays under a still pointer" and "a camera frame with the pointer off the map calls viewChanged"; named rewrite: the plants split's "refreshes Plant Spacing preview after viewport changes" wheels at the pointer, where both behaviours agree (D3). Without navigation under a still pointer nothing differs.
2. **Drafts draw in Pixi** (ADR 0019; today they are DOM boxes, `interaction/overlay-ui.ts:32-72`). Equivalence: the same colour tokens, stroke widths and dash patterns; the DOM `box-shadow` casing (`DRAFT_LINE_CASING`) becomes a Pixi casing stroke of the same colour and width under the line; rectangle and ellipse drafts are world shapes instead of CSS-rotated boxes; labels keep today's chips (spec §1.4, label tones) and Plant a row's ghosts their discs (`GhostEntity` mark `'dot'`); named by-eye deviations remain: polygon vertex markers are `circle-px` `{ radiusPx: 1.75, widthPx: 3.5 }` with the `draft` token (a light disc of radius 3.5 px with a 1 px casing ring, against today's 2.75 px core with a 1.5 px ring), and the band's casing keeps the +2 rule (4 px against today's 5 px); Plant a row's guide has a dashed casing (today a solid casing under a dashed line), the guide and the source ring draw under the row discs (today over them), and the ring sits at the presented radius (today a 2 px border inset in the plant's bounds box); drafts sit in the scene, on top of the scene's content (plants, notes and labels included, as today) and under every piece of DOM chrome (today some previews sit over the handle layer). Test: `renderers/draft-layer.test.ts` plus each tool's `recordingRenderer.lastDraft()` assertions. The live check compares drafts by eye, not by pixels (section 4, phase 0, step 5).

**By-eye conventions (0D2).** Three effects of the coarse view signals ship in 0D2 as conventions, named in its handoff (section 8) and compared by eye, never pixel-matched: (1) the scale ratio, the scale bar and the zoom reached by the scale menu and by "Zoom in to see names" read `ViewReadSurface.groundMetresPerPixel`, three significant figures at the screen centre: the ratio can read one rounding step off when the true value lies within 0.5 % of a boundary (a true 1:144.9 reads 1:150, today 1:140), the bar can move 1 px, those zooms land within 0.5 % of today's, and with no map attached the ground resolution is MapLibre's at the centre latitude instead of `1 / px per m`, under 0.2 % apart; (2) the overview pin is `designPin`, whole pixels: up to 0.5 px from today's; (3) the labels count ("Names shown for 70 of 282 plants in view") re-reads on the settled frame (150 ms after the last camera change, a resize included) and on a zoom-band change, not live during a pan or zoom, since P10 keeps per-frame reads out of `app/`. Label admission itself keeps today's cadence until phase R.

Everything else a user could notice (the GeoLibre selection-drag guard, the Windows HTML5-drop fix) waits for phase F.

**Stop and amend.** If building shows that the design is wrong (an interface cannot carry a case, a MapLibre assumption fails, a policy cannot be written, a phase cannot ship alone), the agent stops, does not work around it, and reports to the main agent. The main agent amends the ADR and the spec in one docs commit, says what changed and why, and tells the user before work resumes. A change that touches the user's data or files (formats, defaults, deletions) is the user's decision, not the main agent's. Under the user's standing permission (2026-09-28) a process rule in AGENTS.md or a guide that blocks a better fix is rewritten in the same change and named in the handoff.

**Tests.** A bug fix carries a regression test written first. A test is deleted only in the commit that adds its replacement, and the bead records where each replacement lives. The counting guard (`desktop/web/scripts/count-vitest-tests.mjs`, section 3.4) runs at the end of every phase-0 sub-phase.

**Gates.** Every sub-phase ends with the frontend gates green on the branch: `cd desktop/web && npx tsc --noEmit && npx vitest run --maxWorkers=4 && npm run test:coverage -- --maxWorkers=4 && npm run check:ui && npm run build && npm run build:web`. Phases 1 and 2 add the Rust and shared-contract gates (phase 1: `LastView.bearing`; phase 2: the `settings.rs` doc comments, which `bindings-gen` copies into `generated/contracts.ts`, committed regenerated with the change) (`cargo fmt --all -- --check`, `CANOPI_SKIP_BUNDLED_DB=1 cargo clippy --workspace --all-targets -- -D warnings`, `CANOPI_SKIP_BUNDLED_DB=1 cargo test --workspace`, `cargo cov` above its floor, `npm run gen:types && npm run check:types`). Docs commits run `python3 scripts/check_docs.py`. No performance gates (user); phase R records measurements in its bead as evidence only.

**Worktrees and disk.** Agents work in worktrees under `.rq-scratch/` with `CARGO_TARGET_DIR=/home/daylon/projects/canopi/.rq-scratch/shared-build/target`. The main agent runs `df -h /` before launching agents and cleans up below about 50 GB free. Merged worktrees and their caches (`/tmp/canopi-*`, headless browser profiles) are removed; screenshots are kept. Review profiles are not caches: they live under `.rq-scratch/reference/<phase>/` and go when the phase's bead closes (section 3.1, step 6).

**Ownership.** One file has one owner per sub-phase (tables below). The main agent owns `__tests__/frontend-architecture-policies.test.ts`, `__tests__/canvas-boundaries.test.ts`, the seams, the test split and counting guard, locale integration, every `bd` write and the worktree's `.beads/issues.jsonl` (section 7, "JSONL"), each phase's Playwright scenario (`desktop/web/e2e/canvas/<phase>.spec.ts`, after canopi-9x95) and every end-of-sub-phase deletion. In the 11 locale files (`i18n/*.json`) an agent adds or removes only its own keys. Nobody edits a file outside their list; a needed edit elsewhere goes to the main agent.

**Stored data.** The only stored-format changes in this plan are `LastView.bearing` in settings (phase 1, `#[serde(default)]`, 0) and the optional `PdfPrintArea.rotationDeg` (phase 1, in memory only today). Both are one-line defaults the user approved; no migration step. `.canopi`, the user DB, the LiDAR catalogue and the plant catalog do not change. Any other stored change stops the work and goes to the user.

**Core exit.** Every phase from phase 0 on (phase 0 as a whole, F, 1, 2, 3 and R) exits with, besides its own Exit bullets: every test named in its section green; its policies green; the strings of its spec §9 table in 11 locales (none for phase 0 and R); the listed docs checked against the shipped code and corrected; its Playwright scenario `desktop/web/e2e/canvas/<phase>.spec.ts` committed (the main agent owns it; the phase's Web check names the steps it automates) and the Chromium and WebKit job green on the pushed commit; the live check and the Web check recorded in the bead; the pre-push review recorded. Section 7 copies the core exit into every phase bead's acceptance.

**Conventions.** Where the spec marks a rule "(convention)", the planner chose it; the handoff of the phase that ships it names it so the user can overturn it (section 8).

## 2. Order

```
28w8 fix (now) ─▶ seams + 9x95 ─▶ 0A ∥ 0D1 ─▶ 0B ─▶ 0C ∥ 0D2 ─▶ 0E ─▶ F ─▶ 1 ─▶ 2 ─▶ 3
                                                                └────▶ R (parallel with F, 1, 2, 3)
```

- The canopi-28w8 standalone fix ships now, before the seams, on its own.
- canopi-9x95 (the Chromium and WebKit CI job, section 3.2) lands beside the seams and is an entry condition of 0A, so every phase from 0A on ends with the CI job, as the definition of done requires.
- 0B needs 0A and 0D1. 0C and 0D2 both need 0B and the main agent's hand-off commit, which holds every edit the two would otherwise share (section 4, 0C), and then run in parallel with disjoint files (0A-2 already moved the app readers of `CanvasQuerySurface.viewport` that 0C owns, so 0D2 does not wait for 0C). 0E needs 0C and 0D2 merged, since it edits files of both. F needs all of phase 0, 0E included (the phase-0 bead closed); phase 1 needs F. R needs 0E merged: 0E's E6 retypes `getAnnotationPresentation`, `getAnnotationScreenFrame` and `PlantPresentationContext.viewport`, whose callers sit in R's files (`renderers/**`, `automatic-detail.ts`, `plant-presentation.ts`, the renderer tests, `chrome/session-chrome.test.ts` and the split-suite handle reads), so 0E runs alone.
- Every sub-phase ships alone: the gates are green on the branch after it. The sub-phases are the seams, 0A, 0D1, 0B, 0C, 0D2 and 0E; 0A-1 and 0A-2 are ordered steps inside the one View stream, merged and pushed once with 0D1 (prompt §15, step 8), and 0A-1 ends on a commit where `tsc` and `vitest` pass in the View worktree. After each sub-phase, a user sees no change until phase F apart from the two named exceptions of section 1 (0B). The legacy camera facade (0A) is what lets 0A ship before 0B, the renderer keep `SceneViewportState` until 0D2, and the old camera's callers wait for 0E.
- Each phase from F on is a release candidate: F, 1, 2 and 3 are each shippable without the next.

## 3. Common procedures

### 3.1 Live check on an isolated review instance

Run from the integration worktree after the phase's gates pass. Never drive the user's own app.

1. Note what already listens: `ss -ltnp | grep -E ':(1420|1431|922[0-9])'`. The user's own `cargo tauri dev` usually holds 1420 and 9223; leave it running and never drive it. If port 1431 is taken by something other than an earlier review instance of yours, stop and ask.
2. Make a profile: `R=/home/daylon/projects/canopi/.rq-scratch/reference/<phase>; mkdir -p $R/{config,data,cache}` (`<phase>` is the phase, not the sub-phase: `phase-0` for all of 0A–0E, `28w8` for the 28w8 checks). It lives under the git-ignored `.rq-scratch/` (`.gitignore:67`), never under `/tmp`, so neither a reboot nor the `/tmp/canopi-*` cache cleanup of section 1 removes the references that later sub-phases compare against; `cp /home/daylon/projects/canopi/.rq-scratch/reference/orchard.canopi $R/orchard.canopi`, plus one empty new Design. Autosave writes into that copy, so restore it from the master (`cp` again) before each comparison. The reference orchard (`.canopi` format v9, 2,200 plants, 24 zones, 106 notes) is a git-ignored, read-only master: copy it into each review profile and never open the master itself in the app. `/home/daylon/projects/canopi/.tmp/dense-canvas-review/orchard.canopi` is not it (format v5, refused below the v7 floor). Never pick a Design from `~/Downloads` or the app's data folders.
3. Launch the review instance from the worktree's `desktop/` directory, with its own identifier (so the single-instance plugin does not hand off to the user's app) and its own Vite port:
   `XDG_CONFIG_HOME=$R/config XDG_DATA_HOME=$R/data XDG_CACHE_HOME=$R/cache CARGO_TARGET_DIR=/home/daylon/projects/canopi/.rq-scratch/shared-build/target cargo tauri dev -f mcp-bridge --config '{"identifier":"com.canopi.review","build":{"devUrl":"http://localhost:1431","beforeDevCommand":{"script":"npx vite --port 1431 --strictPort","cwd":"web"}}}'`
4. Find the bridge port (9223, or the next free one when the user's instance holds 9223) and check its owner: `ss -ltnp` must show the process launched in step 3 (check `/proc/<pid>/exe` and its working directory). Start the MCP driver session on that port.
5. Drive with `webview_interact` (click, double-click, right-click, hover), `webview_keyboard` (press, down, up with modifiers; Space is `"Space"`, since `" "` sends the code `" "`), `webview_screenshot` and `webview_execute_js`. `webview_interact scroll` does not reach the canvas: a wheel is a `WheelEvent` dispatched on the map host through `webview_execute_js`. The bridge has no button-specific drags: drags are dispatched as `PointerEvent` sequences on the map host (`[aria-label="Design map"]`) through `webview_execute_js`, split into separate calls (press, moves, release). They exercise the pipeline, not WebKitGTK's native event order; the native order is covered by the recogniser fixtures and the Playwright job, and the handoff says which was driven.
6. Keep screenshots under `$R/shots/` (the pre-phase references under `$R/shots/reference/`). Remove `$R` only when the phase's bead closes (for phase 0, the commit that closes canopi-f47t.5 after 0E), never when a sub-phase or worktree merges; screenshots are kept (move `$R/shots/` to `/home/daylon/projects/canopi/.rq-scratch/screenshots/<phase>/` and delete the rest of `$R`).

Reference screenshots for "unchanged" checks are taken with the same profile, Design, window size and camera on the commit before the phase. For phase 0 that is the 28w8 fix commit or any later commit before 0A's first commit: the seams commit (types and a test split) and canopi-9x95 (dev dependency, e2e files, CI job, `test.exclude`) change no runtime code, so their pixels are the same. They are an entry condition of 0A, not of the seams; the phase-0 bead records the commit they were taken on and `$R` (`.rq-scratch/reference/phase-0`), and 0A, 0B, 0C, 0D2, 0E and the phase-0 exit all compare against that one profile. The basemap is hidden in the review profile before the references are taken (Map layers, Basemap off: `basemap_visible` is a device setting stored in the profile's user DB, `$R/data/<identifier>/user.db`, so it stays off for every later comparison), because OpenFreeMap tiles load over the network and change on their own; the canvas, grid and chrome are what phase 0 must keep, and the basemap is MapLibre's, not phase 0's.

### 3.2 Web Edition checks (Chromium and WebKit)

Bead canopi-9x95 adds a Playwright job that serves the built Web Edition locally and drives it in Chromium and WebKit on every push. The main agent does it itself, in the integration worktree, right after the seams commit and before 0A: the seams are one short commit, so a parallel "CI" agent would save little and add a worktree and a merge. It is an entry condition of 0A. It owns `desktop/web/package.json` and `package-lock.json` (the `@playwright/test` dev dependency; the bead records why no existing code covers real browser engines), `desktop/web/playwright.config.ts`, `desktop/web/e2e/support/offline.ts` (the network rule under "Web reference"), `desktop/web/e2e/canvas/*.spec.ts` (one scenario file per phase, starting with `base.spec.ts`: open the base fixture, pan, zoom, Present, PDF), `desktop/web/e2e/fixtures/canvas-base.canopi` (a small committed Design: about 20 plants of 4 species, 3 zones, 3 notes and one story step, made in the app on the isolated review instance of section 3.1 (never the user's app) from a new Design and saved by that build, so it carries the build's `CURRENT_CANOPI_FILE_VERSION` (`common-types/src/design.rs`, 9 at `0f05d927`); a later format bump re-saves it in the bump's commit; the orchard is the maintainer's private copy and never enters CI) and the CI workflow job under `.github/workflows/`, plus `desktop/web/vite.config.ts` (`test.exclude: [...configDefaults.exclude, 'e2e/**']`: `vite.config.ts` sets no `test.include`, so vitest's default pattern would collect the `*.spec.ts` files and Playwright's `test()` throws outside its runner; the proof is that the counting guard's `vitest list` names no file under `e2e/`) and `desktop/web/e2e/tsconfig.json`, checked by `npx tsc -p e2e --noEmit` in the Web job (the root `tsconfig.json` includes only `src`). The scenario opens the fixture through Playwright's file chooser; wherever a phase's Web check repeats a live-check step that opens "the orchard copy", the committed job opens this fixture instead, and orchard-scale evidence (phase R frame times) is recorded by hand. Each later phase adds its scenario file. Playwright's `page.mouse` sends real button input (`button: 'right' | 'middle'`), so the job is the standing evidence for the right-click and right-drag order in Chromium (stands in for WebView2) and WebKit (stands in for WKWebView). Limits, recorded in each bead: multi-touch is Chromium-only (CDP `Input.dispatchTouchEvent`); WebKit trackpad `gesture*` events cannot be produced natively and are covered by fixtures E9 and E10.

Serving: `npm run build:web` builds `dist-web` for the `/app/` base with `web.html` as its entry, so the config's `webServer` runs `npx vite preview --mode web --port 4174 --strictPort` (web mode supplies the base and `dist-web`) and `use.baseURL` is `http://localhost:4174/app/web.html`.

Run by hand once the job exists: `cd desktop/web && npx playwright install chromium` (no `--with-deps`), `npm run build:web`, then `npx playwright test e2e/canvas --project=chromium`. WebKit runs locally only in the pinned Docker image below, never with `sudo`: Playwright 1.63's WebKit (build 2359) needs `libavif16`, which this host lacks.

**Web reference.** After canopi-9x95 and the 28w8 fix merge and before 0A starts, the main agent writes `desktop/web/e2e/canvas/phase-0-refactor.spec.ts` (steps 2–6 of the phase-0 live check on the base fixture), runs it and `base.spec.ts` once on the pre-0A commit in the CI job's Linux image with `--update-snapshots`, and commits their `toHaveScreenshot` baselines per engine. The job runs in the official image `mcr.microsoft.com/playwright:v<pinned>-noble` (a job `container:`), so the same image run locally gives the same pixels: Docker is installed and the user is in the `docker` group (checked 2026-09-29); run `df -h /` first (the image is about 2 GB), build with `npm run build:web` in the worktree, then `docker run --rm --ipc=host -v "$PWD":/work -w /work/desktop/web --user $(id -u):$(id -g) -e HOME=/tmp mcr.microsoft.com/playwright:v<pinned>-noble npx playwright test e2e/canvas --update-snapshots` from the worktree root, and remove the image afterwards if space is short. Hiding the basemap in the fixture is not possible (basemap visibility is a device setting, not part of a Design), and masking the map in `toHaveScreenshot` would hide the canvas drawn over it. Those baselines are the phase-0 Web reference; screenshots are taken only on settled states, never mid-drag (drafts are compared by eye, section 1). The orchard screenshots of the pre-job procedure below stay the native reference only.

The 28w8 Web check (by hand, whether or not the job exists yet, since the job never opens the orchard): install Playwright in the review profile, never in the repository: `mkdir -p $R/web && cd $R/web && npm init -y && npm i playwright@<version> && npx playwright install chromium webkit`. ### 3.3 Inventory

The phase bead lists the row IDs it cleared (the seams commit notes its rows on the phase-0 bead), and a phase does not close with one of its rows open unless the inventory re-homes it to a later phase.

### 3.4 The counting guard

`desktop/web/scripts/count-vitest-tests.mjs` (seams commit, main agent) proves that no test was lost while phase 0 moves and replaces tests. It lives beside the other `.mjs` scripts in `desktop/web/scripts/` (the repository-root `scripts/` holds Python only and has no `node_modules`), with its two JSON files beside it: `desktop/web/scripts/canvas-v2-test-baseline.json` and `desktop/web/scripts/canvas-v2-test-replacements.json`. It gets no npm script (`package.json` belongs to canopi-9x95 in the seams window); run it as `cd desktop/web && node scripts/count-vitest-tests.mjs`. The main agent deletes the script and both JSON files in the commit that closes the phase-0 bead (the guard has no role after phase 0); the receipt keeps its last numbers.

- **Collect.** It runs `npx vitest list --json=<tmp file>` in `desktop/web` (vitest 4.1: `list` writes JSON only with `--json`; `--reporter` does not change its output) and reads each test's file and full name (describe path plus title). Several PDF suites read `public/pdf-fonts/*` at import time (`canvas-pdf-text.test.ts:5`), and `npx vitest list` does not run npm's `pretest` hook, so without the fonts `vitest list` exits 1 with ENOENT (checked 2026-09-29). The script first checks that every file of `src/app/canvas-pdf/font-assets.json` exists under `public/pdf-fonts/` and otherwise stops with "run npm run prepare:pdf-fonts" (the worktree setup of prompt §15 step 2 runs it); it never downloads. Any non-zero exit of `vitest list` fails the guard: a partial list is never counted.
- **Record mode (once, seams commit).** `node scripts/count-vitest-tests.mjs --record` writes the baseline. It builds the file list by importing `src/__tests__/support/architecture/source-facts.ts` directly: Node ≥ 22.18 strips types by default and that file imports only `typescript`, so `discoverTypeScriptSourceGraph(new URL('../src/', import.meta.url), 'src')` works from an `.mjs` (checked with Node 22.22.0 on 2026-09-29). The script checks `process.versions.node` first and stops below 22.18 with a message naming that version; `engines` in `package.json` stays `^22.13.0` (CI never runs the script, and `package.json` belongs to canopi-9x95 in the seams window). `policy-harness.ts` cannot be imported this way (extensionless relative imports) and is not needed. The check mode never builds the graph: it compares `vitest list` with the committed baseline and map only.
- **Baseline.** `canvas-v2-test-baseline.json`, committed in the seams commit *before* the split: every test of every baseline file, as `{ file, name }` with `it.each` rows expanded as `vitest list` reports them, and N recorded per file. ## 5. Policy tests

Every new policy rule's `name` (the AST policy's `name`, the regex policy's `it` title in `canvas-boundaries.test.ts`) starts with its P-id and a space, then says what that rule checks, for example `'P5 tools import no MapLibre, DOM or Pixi'`; a row with several rules (P5's `forbid-imports` and `confine-symbols`) gives each its own unique name under the same P-id. The table's Name column titles the row, not the string. The counting guard's map references these exact strings (section 3.4); existing policies keep their names. AST policies go in `__tests__/frontend-architecture-policies.test.ts` with the existing kinds (`__tests__/support/architecture/policy-harness.ts`); each gets a planted-graph negative test in the pattern of that file. `forbid-source-symbols` has no `exceptFrom`, so a symbol rule with exempt files is written as `confine-symbols` (`from` the area, `allowedFrom` the exempt files plus tests). `forbid-source-symbols` and `confine-symbols` match every identifier (`__tests__/support/architecture/source-facts.ts:108`), so confined names must be distinctive. `forbid-calls` compares `targets` globs with the full callee text (`attachment.map.jumpTo`), and records `property` only for member calls, so a bare call (`selectCanvasTool('polygon')`) is caught by `confine-symbols`, not by `properties`. Regex policies go in a new `__tests__/canvas-boundaries.test.ts`, which walks every `.ts`/`.tsx` file under `src/` (as `frontend-architecture-policies.test.ts:2121` does with `readdirSync`), skips tests, applies each regex to every file and compares the hits against the policy's named allowlist; each regex has one planted-file negative test, so a coupling reintroduced in a new file fails. Before an allowlist is written, its bead records the inventory counts, so every allowlist entry is named, with its count and the phase that removes it.
