**How a step is chosen.** These rules come from the audit and apply to every step (AGENTS.md, "Working method"):
- Before a step is built, its brief names the user path or roadmap item behind each planned behaviour; a behaviour with none is dropped, and the drop is named in the handoff. "Useless" means no user path and no roadmap use: before cutting code, a seam or a planned behaviour, check hydrology and catchments (`docs/plans/hydrology.md`, `analysis-registry-and-hydrology.md`), tree and crown detection (`onf-plugin-adaptation.md`, ADR 0012) and LiDAR reading (`docs/guides/data-library.md`: layers, rasters, point clouds, analysis results on the map, hover readouts), and name the item checked in the cut (user, 2026-10-01). What the roadmap needs is kept and adapted toward that need.
- A refactor keeps what users see, not internal mechanisms: a guard, counter, fallback or exact-number test stays only when a user path needs it.
- Nothing is built that a later step of this release replaces (U1).
- The old path goes in the change that replaces it; two paths never run side by side.
- Streams run in parallel only on areas that share no file; coupled work is one sequential stream.
- The spec states contracts and user-visible rules; line numbers belong in briefs. The line numbers already in these documents are hints: each brief re-greps them at its entry HEAD.
- Release scope is settled before a refactor is planned (user, 2026-10-03).
- A risky assumption (a MapLibre or WebKit behaviour, a seam that must carry a new case) is proved by a small throwaway build before a plan is built around it (user, 2026-10-03).
- Up-front specs hold contracts and the user's decisions only; test lists, file rows and wiring belong in the briefs written at the step's entry HEAD (user, 2026-10-03).

**By-eye conventions (shipped in phase 0).** Three effects of the coarse view signals are conventions the user may overturn, compared by eye, never pixel-matched: (1) the scale ratio, the scale bar and the zoom reached by the scale menu and by "Zoom in to see names" read `ViewReadSurface.groundMetresPerPixel`, three significant figures at the screen centre (the ratio can read one rounding step off within 0.5 % of a boundary; with no map attached the ground resolution is MapLibre's at the centre latitude, under 0.2 % from `1 / px per m`); (2) the overview pin is `designPin`, whole pixels; (3) the labels count re-reads on the settled frame (150 ms after the last camera change, a resize included) and on a zoom-band change, not live during a pan or zoom, since P10 keeps per-frame reads out of `app/`. Label admission keeps its cadence until phase R.

**Reviews (user, 2026-10-02).** One review round per step, by one reviewer whose findings are each verified before anyone fixes them. A second round runs in three cases: on the fix diff alone whenever a review's findings changed code (in phase 0 a fix brought a regression only that check caught); a full second round on work that touches the user's files or stored data, on phase 1's rotation core, and on any step whose first round found a blocker or a major finding; never more than two full rounds on one diff (a third points at the design or the tests). The pre-push review of everything since the last push stays.

**User decisions.** A decision the user made, recorded with its date, changes only when the user changes it. An agent that finds one in its way stops and reports it; reviews check that the docs still say what the user decided (phase 0: a merged rewrite reversed the user's stored-data permission until the review caught it).

**Stop and amend.** If building shows that the design is wrong (an interface cannot carry a case, a MapLibre assumption fails, a policy cannot be written, a step cannot ship with its gates green), the agent stops, does not work around it, and reports to the main agent. The main agent amends the ADR and the spec in one docs commit, says what changed and why, and tells the user before work resumes. The `.canopi` format and local data (the user DB, Drafts, Web storage, the LiDAR catalogue) may change when that improves the project, without asking the user first, and each change is named in the handoff (ADR 0021, "Later format changes"; user, 2026-10-02); after 2.0 a format change decides between refusing older files and a migration case by case, with no ladder by default. Under the user's standing permission (2026-09-28) a process rule in AGENTS.md or a guide that blocks a better fix is rewritten in the same change and named in the handoff.

A test is deleted only in the commit that adds its replacement, or that retires it with the reason no user sees what it checked, named in the commit; the bead records where each replacement lives. ## 3. Common procedures

### 3.1 Live check on an isolated review instance

Run after the phase's gates pass, from a worktree no other agent edits during the check (`git worktree add --detach .rq-scratch/canvas-v2-live <commit>`, removed afterwards): the review instance's Vite hot-reloads any edit, so a fix written in the same worktree changes the code under test mid-check (phase 0, 0E). Never drive the user's own app.

1. Note what already listens: `ss -ltnp | grep -E ':(1420|1431|922[0-9])'`. The user's own `cargo tauri dev` usually holds 1420 and 9223; leave it running and never drive it. If port 1431 is taken by something other than an earlier review instance of yours, stop and ask.
2. Make a profile: `R=/home/daylon/projects/canopi/.rq-scratch/reference/<phase>; mkdir -p $R/{config,data,cache}` (`<phase>` is the phase: `phase-F`, `phase-1`, …). It lives under the git-ignored `.rq-scratch/` (`.gitignore:67`), never under `/tmp`, so neither a reboot nor the `/tmp/canopi-*` cache cleanup of section 1 removes the references a phase compares against; `cp /home/daylon/projects/canopi/.rq-scratch/reference/orchard.canopi $R/orchard.canopi`, plus one empty new Design. Autosave writes into that copy, so restore it from the master (`cp` again) before each comparison. The reference orchard (`.canopi` format v9, 2,200 plants, 24 zones, 106 notes) is a git-ignored, read-only master: copy it into each review profile and never open the master itself in the app. `/home/daylon/projects/canopi/.tmp/dense-canvas-review/orchard.canopi` is not it (format v5, refused: Canopi 2.0 opens only v9). Never pick a Design from `~/Downloads` or the app's data folders.
3. Launch the review instance from the worktree's `desktop/` directory, with its own identifier (so the single-instance plugin does not hand off to the user's app) and its own Vite port:
   `XDG_CONFIG_HOME=$R/config XDG_DATA_HOME=$R/data XDG_CACHE_HOME=$R/cache CARGO_TARGET_DIR=/home/daylon/projects/canopi/.rq-scratch/shared-build/target cargo tauri dev -f mcp-bridge --config '{"identifier":"com.canopi.review","build":{"devUrl":"http://localhost:1431","beforeDevCommand":{"script":"npx vite --port 1431 --strictPort","cwd":"web"}}}'`

Drive with `webview_interact` (click, double-click, right-click, hover), `webview_keyboard` (press, down, up with modifiers; Space is `"Space"`, since `" "` sends the code `" "`), `webview_screenshot` and `webview_execute_js`. `webview_interact scroll` does not reach the canvas: a wheel is a `WheelEvent` dispatched on the map host through `webview_execute_js`. They exercise the pipeline, not WebKitGTK's native event order; the native order is covered by the recogniser fixtures and the Playwright job, and the handoff says which was driven.
6. Keep screenshots under `$R/shots/` (the pre-phase references under `$R/shots/reference/`). Remove `$R` only when the phase's bead closes, never when a step or worktree merges; screenshots are kept (move `$R/shots/` to `/home/daylon/projects/canopi/.rq-scratch/screenshots/<phase>/` and delete the rest of `$R`).

### 3.2 Web Edition checks (Chromium and WebKit)

## 5. Policy tests

Every new policy rule's `name` (the AST policy's `name`, the regex policy's `it` title in `canvas-boundaries.test.ts`) starts with its P-id and a space, then says what that rule checks, for example `'P5 tools import no MapLibre, DOM or Pixi'`; a row with several rules (P5's `forbid-imports` and `confine-symbols`) gives each its own unique name under the same P-id. The table's Name column titles the row, not the string. Existing policies keep their names. AST policies go in `__tests__/frontend-architecture-policies.test.ts` with the existing kinds (`__tests__/support/architecture/policy-harness.ts`); each gets a planted-graph negative test in the pattern of that file. `forbid-source-symbols` has no `exceptFrom`, so a symbol rule with exempt files is written as `confine-symbols` (`from` the area, `allowedFrom` the exempt files plus tests). `forbid-source-symbols` and `confine-symbols` match every identifier (`__tests__/support/architecture/source-facts.ts:108`), so confined names must be distinctive. `forbid-calls` compares `targets` globs with the full callee text (`attachment.map.jumpTo`), and records `property` only for member calls, so a bare call (`selectCanvasTool('polygon')`) is caught by `confine-symbols`, not by `properties`. Regex policies go in `__tests__/canvas-boundaries.test.ts`, which walks every `.ts`/`.tsx` file under `src/` (as `frontend-architecture-policies.test.ts:2121` does with `readdirSync`), skips tests, applies each regex to every file and compares the hits against the policy's named allowlist; each regex has one planted-file negative test, so a coupling reintroduced in a new file fails. Before an allowlist is written, its bead records the inventory counts, so every allowlist entry is named, with its count and the phase that removes it.
