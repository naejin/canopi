## Invariants

1. Only a complete, applicable, admitted observation can satisfy an obligation. Missing mandatory evidence is inconclusive. Invalid evidence/declarations or measured violations fail. Known failure outranks every independent gap at every layer.
2. Parse typed values before use. Booleans are not strings/numbers; counters are finite non-negative integers; timestamps and measurements are finite with declared units. Never use truthiness or silently drop malformed values to obtain a pass.
3. Source bytes, role, artifact, fixture, environment and observation refer to the same evidence. Expectations come from the accepted declarations, not the report being checked. Each source is read once per evaluation; decoding, digest, admission and observations use that snapshot. A consistency check is not attestation that a physical experiment occurred.
4. Missing and corrupt inputs differ. Every readable malformed input yields a structured diagnostic/nonzero qualification outcome, not a traceback or a fabricated empty success. If the output itself cannot be written, exit nonzero with a clear stderr error; never claim an output was saved.
5. Requirements combining multiple sources/runs retain all required coverage and the worst applicable outcome. Adding irrelevant information cannot satisfy a requirement; adding a gap cannot erase an independently present failure. Identical and conflicting duplicate keyed evidence are invalid.
6. Normal CLI and programmatic evaluation use the same validated path. Synthetic controls require an explicit test-only mode, never a production qualification switch. Bare strings saying pass, or a boolean saying build reproduced, are not substitutes for the required supporting evidence.

## Input inventory and verdict policy

Cover inputs actually consumed by the admission pipeline, not arbitrary future schemas: requirement contract; candidate pins/role declarations; per-role fixture manifest; raw report envelope and identity; assertions/preconditions/negative controls; artifact/build/sidecar evidence; ledger/window observations; display runs/counters/latencies; candidate/reference resource records; assembled bundles and CLI filesystem paths.

Absent required field/file means inconclusive. Present invalid type, invalid value, conflicting identities or duplicate key means fail. Legacy absent result/identity remains a gap, but any readable positive failure still fails. Explicit null is invalid unless that field's documented schema permits it as unavailable; unavailable observations remain gaps. Optional absent fields do not block; optional unknown fields are retained or reported but cannot suppress a known violation. Reject non-standard JSON NaN/infinity and duplicate keys before they can disappear in decoding. Validate the authored requirement contract's structure/types/unique IDs too; do not alter which scientific obligations are mandatory.

Negative controls use explicit scoped expected outcomes; an expected rejection is successful execution of that control, not a positive capability. Do not let an arbitrary failure-prefix label exempt a mandatory positive assertion. Report diagnostic input defects separately from measured engine violations.

## Acceptance and deferral boundary

Blockers: false capability/qualification pass, hidden independently known failure, rejection of a contract-valid control, uncaught expected input error or absent diagnostic artifact on a writable destination, and runner bypass of eligibility. Non-blockers: warning cleanup, optional refactors, naming/style, additional future formats, unavailable real engine/platform measurements already honestly blocked. File those separately in bd; do not expand this repair to address them.

Acceptance requires all eight rows traced to tests, adversarial self-review through the real CLI, focused gates green and independent review. The implementation receipt should list only actual evidence and residual limitations. Acceptance of this repair does not accept Q, integrate the branch, approve new experiments or start N1.
