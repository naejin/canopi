T2 - per-run completeness and precedence
--------------------------------------------------------------------------

RED

  $ node --test dist/tests/t2RunReduction.test.js
  not ok 2 - every required per-run field is mandatory for every candidate run
  not ok 3 - an over-limit value fails even when its record has a sampling gap
  not ok 5 - a missing per-run observation is a gap rather than a fabricated pass
  not ok 6 - a malformed per-run value fails rather than being skipped
  not ok 7 - an unsupported budget observation leaves a gap rather than a pass
  # pass 3 # fail 5

GREEN

  Three changes, each addressing one half of the family:

  1. `incrementalPeakRssMiB` joined the mandatory per-run observations. It is a
     per-run peak, so a run that omits it cannot evidence the combined bound, and it
     is not filled in from a different run.
  2. Every leaf is classified into three outcomes rather than two — usable,
     present-but-unusable (invalid input, fails), and absent (a gap). An explicit
     `null` is present, so it fails; the sampling leaves are named in the gap reason.
  3. The budget check reads **every** record that recorded the counter, whether or
     not that record sampled correctly. A measured over-limit value is a fact about
     the engine, and discarding it because the same record has a gap loses a known
     failure. A zero-result probe is what forced this case into existence (see G4
     below).

  $ node --test dist/tests/t2RunReduction.test.js
  # pass 10 # fail 0

Display disk cache. No producer emits a display disk-cache observation, so the plan's
512 MiB bound cannot be established from these records. The requirement now carries an
explicit, unconditional gap:

    the plan's display disk-cache bound (512 MiB) is not established: no producer
    emits a display disk-cache observation, so its compliance is unmeasured

The gap is stated unconditionally rather than inferred from the absence of a field
name: a field name is this consumer's guess, and accepting one would let a caller
establish the plan's bound by inventing a key. The probe confirms that supplying
`displayDiskCacheBytes` at 1 GiB, 1, or 0 leaves the requirement inconclusive, so the
caller cannot move it in either direction.

Consequence, recorded rather than hidden: `Q-RES-1` moved out of the supported set in
the test fixture. Its five contract assertions are all decidable and correct; the
*requirement* is permanently a gap because one dimension of the plan's budget has no
observation. Calling it supported would have required fabricating that observation.

--------------------------------------------------------------------------
Evidence mutation sweep
--------------------------------------------------------------------------

`tests/mutationSweep.test.ts` applies 32 mutations to one consumed field of the
coherent control and checks three independent things per mutation:

  - the verdict of the **target assertion**, read from the promoted assertions or
    from `observed` when the source was not admitted;
  - the **requirement verdict**, declared separately for every mutation so the two
    can never be conflated;
  - every **unaffected requirement**, which must not move.

Mutation kinds: remove; duplicate identically; duplicate conflictingly; corrupt
type/value; substitute unrelated identity; and known-failure-plus-gap combinations at
declaration, source, assertion and display-run levels. There are no inapplicable
mutations to mark: every field listed is consumed by a mapping, which is why it is in
the list.

  $ node --test dist/tests/mutationSweep.test.js
  # pass 7 # fail 0

Three defects in the agent's **own expectations** were found by the sweep and are
recorded here because they are the point of running it:

  1. Several mutations were expected to change the target assertion when they are
     carried by the source's own admission instead. A conflicting artifact identity
     fails the requirement while the window assertion it accompanies keeps its own
     verdict. Fixed by declaring the requirement verdict separately for every
     mutation.
  2. Two cases asserted an interaction that cannot occur: the "gap" removed the same
     field the "over-limit" value lived in (a contradiction in terms), and the
     fixture-hash conflict was expected to move the window assertion. Both were
     replaced with cases on genuinely independent paths.
  3. One case claimed a differently-labelled `validity:` record could not substitute
     for a required record. It can: the declared contract is prefix-based for
     validation outcomes, and the record is a real validation outcome for the same
     fixture. The mutation was renamed to what it actually tests. The genuine
     substitution defect — an unrelated name standing in for a *required artifact* —
     is covered in T3 and does fail.

No counterexample in the production code was found by the sweep.

Guard-removal sensitivity
--------------------------------------------------------------------------

Each probe reverts one guard in a working tree, rebuilds, runs the emitted suite, and
restores. Reported honestly, including zero results and environment failures.

  G1  duplicate role detection disabled ......................... 3 failing
  G2  duplicate role reported as a gap rather than a failure ..... 2 failing
  G3  memory dropped from the required observations .............. build failure
      (the comparison no longer type-checked; not a meaningful probe)
  G4  budget check restricted to sampled records again ........... 0 failing  <-- ZERO
  G5  per-artifact records replaced by prefix matching ........... 3 failing
  G6  sidecar survival observation not required .................. 1 failing
  G7  sidecar digest shape not validated ......................... 1 failing
  G8  unpinned engine name not compared ........................... 2 failing
  G9  negative durations accepted ................................ 1 failing
  G10 incomplete records no longer a gap ......................... 4 failing
  G11 null treated as missing rather than malformed .............. 2 failing

**G4 was a genuine gap in the agent's tests, not redundant defence.** Reverting the
budget check to sampled records only left every test green, because every over-limit
case in the T2 matrix had a *second, healthy* candidate run — so even without the fix
the requirement still failed for another reason and the case could not tell the
difference. Two cases were added: an over-limit value in an unsampled record with a
healthy run present (both orders), and the inverse. G4 now fails one test, so the
guard is load-bearing and its test is effective.

G3 is reported as a build failure rather than a result: removing `incrementalPeakRssMiB`
from the array made a later comparison type-unprovable, which is the compiler catching
the edit rather than a test catching the behaviour. It is not counted as coverage.

No probe was skipped for lack of time or environment. Child-process capture worked
throughout; the review's reported `EPERM` did not recur in this round.
