Q declaration and precedence repair — captured cycle evidence
=============================================================

Baseline 35c6166b. Commands run from the repository root. Outputs are trimmed to
the decisive lines. Each RED observation was captured before the corresponding
change; each sensitivity probe was captured by reverting one guard in a working
tree, observing the failures, and restoring the file. Nothing here is
reconstructed after the fact.

Every cycle was driven from one proven passing control through the raw report,
the real assembler and the real gate. Expected values were written down before
the code under test was run, and no oracle in these cycles is computed by the
module being tested.

Test-count progression: 168 (baseline) -> 180 (declaration validation added)
-> 187 (CLI declaration path) -> 205 (precedence and result-independence)
-> 209 (combined-fault probes).

--------------------------------------------------------------------------
R5-01 fixture manifest and pin declarations
--------------------------------------------------------------------------

RED (intended cause: `validate_fixture_manifest` did not exist, so a declaration
was indexed directly into a dict and a set)

  Before any declaration validation existed, each of these returned `pass`:

  - a declaration listing the same fixture name twice with different hashes,
    in either order: whichever entry came last silently won, so the defect was
    order-dependent (`bad-first` => pass, `bad-last` => fail);
  - a declaration listing the same fixture name twice with the *same* hash;
  - a declaration whose member was the string "a" rather than an object, which
    was misreported downstream as "undeclared fixture 'a'";
  - a declaration recording no hash at all;
  - a declaration with an explicit empty `requiredFixtures: {"q2": []}` list,
    which waived the raster evidence requirement entirely.

  The same class of bypass existed for the pin declaration: `{"lib": "p",
  "lib": "q"}` collapsed to `"q"` under normal JSON decoding, and the report was
  judged against whichever pin was written last.

GREEN (one validated declaration path)

  `validate_fixture_manifest`, `validate_fixture_manifest_text`,
  `validate_pin_declaration` and `validate_pin_declaration_text` in
  `qualification_evidence.py`. Decide after collecting every independently
  evaluable finding: missing manifest or missing hash => inconclusive; malformed
  type or value, duplicate identity (including identical), conflicting entries,
  undeclared required reference, repeated JSON object key, explicit empty
  required list => fail.

  $ python3 -m unittest discover -s scripts/raster-qualification/tests
  Ran 180 tests ... OK

  $ python3 -m unittest discover -s scripts/raster-qualification/tests -p "`test_cli_integration.py`"

  FAIL: test_duplicate_pin_key_is_rejected_rather_than_last_write_winning
  FAIL: test_malformed_member_type_is_rejected_with_a_nonzero_result
  FAIL: test_required_reference_to_an_undeclared_fixture_is_rejected
  Ran 12 tests ... FAILED (failures=4)

  This is the RED for the CLI half: the programmatic assembler rejected the
  declaration while `measure.py gate-assemble` still exited 0. Production must
  not be weaker than the tests.

  GREEN after `load_fixture_manifest` and `load_declared_pins` were routed
  through the same validators and a rejection became a nonzero result with the
  diagnostic bundle written first:

  $ python3 -m unittest discover -s scripts/raster-qualification/tests
  Ran 187 tests ... OK

  Real CLI confirmation (temporary root, not the private evidence directory):

  $ python3 scripts/raster-qualification/measure.py gate-assemble \
        --reports <tmp>/reports --host chromium \
        --fixture-manifest <tmp>/fixture-manifest.json --out <tmp>/bundle.json

  rc: 0

  `load_fixture_manifest` collapsed a rejected declaration into `None`, the same
  shape as an absent one. Fixed by returning the `DeclarationValidation` itself

  points run the identical path and a rejection keeps its own verdict.

  After the fix, the same command writes a bundle whose
  `declarations.fixtureManifest.verdict` is `fail`, exits 2, and prints
  `invalid declaration: ...` without a traceback.

R5-02 gap-based early return
--------------------------------------------------------------------------

RED (intended cause: `admit_report` reduced to a verdict and returned before the
identity comparisons ran)

  Reproduced before the change, driven through the real assembler and gate:

  - wrong observed fixture hash + `runId` removed
      verdict = inconclusive
      reasons = ['... identity does not record a nonempty runId']
    The hash conflict is *lost entirely*: the conflict is never compared, so the
    reviewer cannot see it.
  - wrong observed fixture hash + no declared manifest
      verdict = inconclusive, conflict never compared.

  The defect was order-dependent: whichever field the reader examined first
  decided whether the comparison happened at all.

GREEN (collect, then reduce once)

  `admit_report` no longer sets a verdict inside any section. Every section
  appends to `failed`/`gaps` or to the `conflicts`/`blocked` collectors, and the
  precedence fail > inconclusive > pass is applied once at the end.

  Same two cases after the change:

  - wrong hash + missing runId
      verdict = fail
      reasons = ['... identity does not record a nonempty runId',
                 "... fixture 'derived_cog' hash conflict: expected 'aaa...',
                  observed '999...'"]
  - wrong hash + no declared manifest: the route conflict is still reported, and
    the missing declaration is reported as its own gap.

  $ python3 -m unittest discover -s scripts/raster-qualification/tests
  Ran 205 tests ... OK

Isolated guard-removal sensitivity (R5-02)

  Probe A: reinstate `if gaps: result.verdict = UNKNOWN; return result` before
  the comparisons.

  $ python3 -m unittest discover -s scripts/raster-qualification/tests
  Ran 209 tests ... FAILED (failures=36)

  Distinct failing methods under probe A, by class:

    CombinedFaultSensitivity    1   test_every_contributed_finding_survives_the_reduction
    AdmissionPrecedence        27   both cross-product orders plus the monotonicity
                                    invariant, for every conflict/gap pair
    ResultIndependentFailures   4   recorded failure, failed assertion and failed
                                    precondition with an absent result

  Probe B: keep the reduction but stop carrying the collected conflict reasons
  into `result.reasons`.

  $ python3 -m unittest discover -s scripts/raster-qualification/tests
  Ran 209 tests ... FAILED (failures=26)

  Distinct failing methods under probe B:

    CombinedFaultSensitivity    1   test_every_contributed_finding_survives_the_reduction
                                    (subtest: finding='route conflict')
    AdmissionPrecedence         3   the route, environment and artifact-version
                                    conflicts, in both cross-product orders, plus
                                    the monotonicity invariant
    ResultIndependentFailures   0

  The first version of the combined probe did *not* catch probe B. It stacked only
  the fixture-hash conflict, which reaches `reasons` through the fixture checks
  rather than through the conflict collector, so it could not see a dropped
  conflict list - and the isolated tests that could see it (route, environment,
  artifact version) already existed. The combined probe now stacks *two* conflicts
  on different code paths (fixture hash and route) plus the gaps and the recorded
  failures, and probe B fails it.

  That is the value the combined probe adds over the isolated ones: it is the only
  check that fails when *any* single collector's contribution is dropped, and it
  covers the composed case where two conflicts reduce to one verdict while the
  isolated tests are each satisfied by a different path.

R5-03 findings independent of `result`
--------------------------------------------------------------------------

RED (intended cause: the report's own failures were gated on the `result` field,
and containers were iterated without a shape check)

  Reproduced before the change, driven through the real assembler and gate:

  - positive failure list, `result` key absent
      verdict = inconclusive, positive_failures = ['measurement aborted']
    The recorded failure was not surfaced as a failure.
  - `"result": null` (present but unusable)
      verdict = inconclusive
    An explicit null was treated exactly like an absent key.
  - failed assertion (`{"name": "range-bytes-served", "ok": false}`) with
    `result` absent
      verdict = inconclusive
  - malformed `failures` container (the string "not-a-list")
      verdict = fail, but with the nonsense reason
      '... records failures: n; o; t; -; a; l; i; s; t'
    The string was iterated character by character.

  A second run of the same probe class found a crash rather than a wrong verdict:
  a malformed `assertions` container raised
  `TypeError: string indices must be integers` from inside `assemble`, and a
  malformed `preconditions` container was read as *no unmet preconditions* and
  the requirement passed.

GREEN (read the record, not the summary)

  `_scan_failures`, `_failed_assertions`, `_scan_preconditions`,
  `_named_assertions`, `_texts` and `_failure_texts` in
  `qualification_evidence.py`. Absent `result` stays a gap; present-but-unusable
  `result` (including explicit null) is invalid; recorded failures, failed
  assertions and failed preconditions are failures whatever the summary says;
  malformed containers are input failures, never silent empty lists.

  $ python3 -m unittest discover -s scripts/raster-qualification/tests

  assertions=list-of-str           CRASH -> fail

Isolated guard-removal sensitivity (R5-03)

  Probe C: remove the container shape checks (so a malformed container is iterated
  again) and gate the recorded findings on an absent `result` again.

  $ python3 -m unittest discover -s scripts/raster-qualification/tests
  Ran 209 tests ... FAILED (failures=3, errors=1)

  Distinct failing methods under probe C:

    test_malformed_failures_container_is_an_input_failure

  rather than attributing each failure to one line. The per-behavior RED
  observations above are what establish the individual causes.
